# 文件上传与审批附件方案

> 状态：待实施方案。当前只确定接口和数据边界，不修改代码、数据库或远程对象存储。

## 1. 目标

业务方先调用审批中心的批量上传接口，一次提交多个文件并获得对应的 `file_ids`。发起审批时在请求顶层提交这些 `file_ids`。审批中心验证整组文件后创建审批实例，并把文件与实例固定关联。审批与抄送详情可以查看和下载这些申请材料。

附件区对所有审批流**默认可用、默认非必填**，无需在每个流程的 `form_schema` 中添加文件字段。以后某条流程需要“合同必须上传”时，再添加流程级附件规则。本期仅处理申请材料；审批意见附件、节点专属附件留待后续需求。

## 2. API 契约

### 2.1 批量上传文件

```http
POST /api/files
X-API-Key: <业务方租户密钥，租户模式必填>
Content-Type: multipart/form-data

files=<采购合同.pdf 的二进制内容>
files=<报价单.xlsx 的二进制内容>
```

`files` 是可重复的 multipart 字段，一次接收 1 到配置上限个文件；单文件上传也走同一个接口。返回顺序与上传顺序一致。成功返回 `201`，响应沿用项目的 `{code, msg, data}` 包装：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "file_ids": [
      "9bbd1155-918c-4a5b-9802-273957004f6e",
      "8a098818-56a5-47a9-aec3-21ca2babcd93"
    ],
    "files": [
      {
        "file_id": "9bbd1155-918c-4a5b-9802-273957004f6e",
        "file_name": "采购合同.pdf",
        "content_type": "application/pdf",
        "size_bytes": 245760,
        "sha256": "第一个文件的内容摘要",
        "uploaded_at": "2026-09-29T09:00:00Z"
      },
      {
        "file_id": "8a098818-56a5-47a9-aec3-21ca2babcd93",
        "file_name": "报价单.xlsx",
        "content_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        "size_bytes": 98304,
        "sha256": "第二个文件的内容摘要",
        "uploaded_at": "2026-09-29T09:00:00Z"
      }
    ]
  }
}
```

**整批成功或整批失败**：先检查全部文件的数量、大小和类型，再写入对象存储；所有文件本体与元数据均成功后才返回整组 `file_ids`。任一文件失败，接口不返回部分成功的 ID，已写入的对象尽力删除；清理失败的孤儿对象由定期对账任务按批次对象键前缀找出并删除。错误响应标出失败文件在 `files` 中的位置与原因，业务方修正后重传整批。对象键由服务端生成批次前缀与 UUID，不使用原文件名作为存储路径；原文件名仅用于展示与下载文件名。

### 2.2 发起审批

原接口 `POST /api/processes/{process_id}/instances` 增加可选的顶层字段 `file_ids`，省略等同于空数组，保持现有无附件调用有效：

```json
{
  "business_key": "PO-2026-001",
  "title": "采购申请",
  "applicant_person_id": "11111111-1111-1111-1111-111111111111",
  "approval_form": {"amount": 10000},
  "execution_payload": {},
  "file_ids": ["9bbd1155-918c-4a5b-9802-273957004f6e"]
}
```

发起前逐个校验：UUID 格式、无重复、文件记录存在、文件状态为 `READY`、对象仍存在、文件归属当前可信租户，且总数量在上限内。任意一个无效，整次请求返回 `422`，在响应中列出对应位置和 `file_id`；不存在时明确返回“file_id 不存在”，不可用或跨租户时返回“file_id 不存在或无权使用”，不暴露其他租户的文件信息。**不创建审批实例、首批任务或使用记录。**

`file_ids` 参与当前请求摘要的幂等比较：同一租户、流程、`business_key` 重复提交相同内容与相同文件列表，返回已有实例；文件列表变化则按现有规则返回 `409`，不能悄悄修改已发起的审批单。

### 2.3 查询与下载

- 现有审批详情和工作台任务关联详情增加 `attachments` 列表，包含 `file_id`、文件名、类型、大小、上传时间；不返回存储桶、对象键或永久公开 URL。
- 业务方使用租户密钥查询/下载文件；管理端详情使用管理密钥下载。两类入口都重新校验文件归属或审批单访问范围。
- 下载由后端鉴权后流式转发，或签发短有效期的对象存储下载 URL；第一版可采用后端流式转发，避免把对象存储权限交给调用方。
- 审批、抄送页面展示同一组申请材料并提供下载；抄送页面仍没有修改权限。

## 3. 数据模型与事务

文件模块使用独立的 `file` Schema：

| 表 | 主要字段 | 用途 |
| --- | --- | --- |
| `file.file_record` | `id`、`tenant_id`（全局模式可空）、`object_key`、`file_name`、`content_type`、`size_bytes`、`sha256`、`status`、`uploaded_at` | 文件元数据；文件本体不进数据库 |
| `file.approval_attachment` | `id`、`file_id`、`approval_instance_id`、`position`、`attached_at` | 审批实例与文件的关联，`(approval_instance_id, file_id)` 唯一 |

关联表由文件模块持有。沿用项目现有模块边界，不对 `process.approval_instance` 建跨 Schema 外键；同一事务内先确认实例和文件，再写关联。文件可以被同一租户的多个审批实例引用，但本体不可覆盖，历史审批单始终指向上传时的那份内容。全局模式的文件只能由全局模式引用，租户模式不能引用它。

`ApprovalStartRequest` 增加 `file_ids: list[UUID]`。文件模块提供“校验并绑定到实例”的服务方法，在现有审批发起事务中调用，位置在实例已创建但尚未提交时。审批实例、节点执行、任务、租户使用记录及附件关联**同一次提交或同一次回滚**。校验应在创建实例前完成；绑定阶段再锁定文件记录，防止并发清理造成悬空引用。重复发起命中已有实例时只做请求摘要比对，不再次插入关联。

上传与发起是两次独立请求，不能做成一个数据库事务。上传成功而发起失败时，文件保持未关联状态，业务方可修正请求继续使用该 ID。以后清理超过保留期且从未关联的文件；已关联文件不得按临时文件策略删除。清理需要先将记录标记为不可引用，再删除对象本体，避免与正在发起的审批竞争。

## 4. 存储实现与模块边界

```text
app/server/file/
  api/                   # 上传、查询、下载接口及租户/管理端鉴权
  src/config/            # 大小、类型、存储驱动、对象存储配置
  src/schemas/           # 上传响应、附件展示和错误模型
  src/models/            # 文件元数据及审批关联
  src/repository/        # 文件和关联记录查询
  src/service/           # 上传、校验、绑定、下载与清理
  src/storage/           # Storage 协议、S3 兼容实现、本地开发实现
  docs/                  # 本方案
```

正式部署使用**私有 S3 兼容对象存储**（云 OSS 或内网对象存储均可）；PostgreSQL 保存元数据和关联。开发环境可选择本地目录驱动，但目录必须在 Git 项目之外，并明确备份和清理策略。两个驱动使用同一 `Storage` 接口，不把存储供应商细节传入流程模块。AI 平台的 `/file/upload` 用于 Agent 临时附件，不作为审批材料原件存储。

批量上传先流式检查并暂存整批文件，再写入私有对象；全部对象上传成功后，在同一个数据库事务中写入所有 `READY` 元数据。数据库写入失败时尽力删除本批对象，并记录待清理的孤儿对象。单文件大小、单批数量、单批总大小、单审批附件数量和允许类型由配置控制。第一版建议默认单文件 20 MiB、单批及单审批最多 10 个、单批合计 100 MiB，允许 PDF、常见图片、DOCX、XLSX；这些值在实施时可根据业务样本调整。不要只信客户端 MIME 类型，服务端也要检查扩展名与实际内容。存储桶不开放公共读取，不返回永久 URL。

## 5. 权限边界

- 上传接口复用现有业务接入的 `X-API-Key` 解析可信 `tenant_id`。请求体不接受 `tenant_id`，`file_id` 为不可猜测的 UUID，但 UUID 本身不是授权凭证。
- 发起时除“存在”还必须验证租户归属，否则一个业务方可通过别人的 `file_id` 引用其文件。当前业务系统只有租户级身份；未来接入个人登录后，再补上传人及单据参与者级下载权限。
- 管理端查看和下载沿用现有 `X-Admin-Key`。审批详情与抄送详情只展示已绑定文件，不通过文件列表泄漏其他上传内容。
- 文件不直接作为业务执行回调的请求体；回调需要文件时，应按明确的授权接口取文件，而非把对象存储地址塞进 `execution_payload`。

## 6. 实施及验收顺序

1. 建立 `app/server/file` 的模型、存储接口和后端配置；新增 `data/init.sql` 幂等结构与一份只新增表/索引的迁移脚本。**不自动执行现有远程数据库迁移。**
2. 完成批量上传、元数据、下载及租户鉴权；在本地目录驱动和 S3 兼容驱动下保持同样接口行为，单文件也使用批量接口。
3. 扩展审批发起请求，在现有事务中校验并关联全部 `file_id`，把文件列表计入幂等摘要；详情响应返回附件元数据。
4. 更新联调页的发起表单、审批详情和抄送详情；同步更新业务接入指南中的上传与发起示例。
5. 验证无附件旧请求、有效单/多文件、批量中途失败无部分成功、缺失文件、跨租户文件、重复 ID、上传后发起失败、幂等重放及并发发起。迁移由用户在选定数据库执行后再做真实库联调。

核心验收：一次上传得到完整的 `file_ids`，批量失败不返回部分 ID；发起携带全部有效 ID 后，审批和抄送详情可看到并下载原件；任何一个 ID 不存在或无权使用时，审批创建失败且没有半成品记录。
