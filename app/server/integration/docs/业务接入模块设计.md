# 业务接入模块设计

> 设计状态：已确认  
> 开发状态：已完成，实现说明见本文第 18 节

## 1. 文档目标

本文档定义业务系统如何接入审批中心、如何获得审批流使用权限、如何发起审批，以及
审批中心如何保存业务系统与审批实例之间的关系。

本模块解决的是“谁使用哪条审批流、以什么业务动作发起了哪次审批”。审批流程的定义
和推进仍由 `process` 模块负责；审批通过后的 HTTP 调用、重试和执行日志由后续
`callback` 模块负责。

## 2. 已确认的原则

1. 一个租户代表一个接入审批中心的业务系统。
2. 业务系统使用 `X-API-Key` 调用审批中心，`tenant_id` 不由请求体传入。
3. 业务系统发起审批时必须提供稳定的 `process_id`，不提供版本 ID。
4. 租户与审批流是多对多关系，租户只能使用已经启用绑定的审批流。
5. 审批流节点及审批人全部由流程版本决定，租户绑定不覆盖流程配置。
6. 每次成功发起审批都保存租户使用记录，并关联唯一的审批实例 ID。
7. `process` 和 `integration` 业务表不保存 `tenant_id`，租户关系统一保存在
   `tenant` Schema。
8. `TENANCY_ENABLED=false` 时不要求 API Key，也不创建租户绑定和使用记录，审批
   核心能力仍然可以在全局模式下运行。
9. 审批通过时只产生业务执行任务，不在审批事务中直接调用外部 HTTP 接口。
10. `approval_form` 用于审批展示，`execution_payload` 用于业务执行，两者分开校验和
    保存。

## 3. 模块边界

业务接入能力需要三个现有 Server 协作，但各自维护自己的数据：

| Server | 本次职责 |
| --- | --- |
| `tenant` | API Key 身份、流程授权、业务动作授权、审批使用记录 |
| `integration` | 业务动作定义、请求参数规则、调用接口配置 |
| `process` | 审批实例创建、版本绑定、表单校验和流程推进 |

调用方向为：

```text
业务接入 API
    → TenantScope 校验租户与流程绑定
    → integration 校验 action_code 和 execution_payload
    → process 创建并推进审批实例
    → TenantScope 保存审批使用记录
```

`process` 模块不直接查询 tenant 表，`integration` 模块也不直接解析 API Key。租户
能力统一通过依赖注入得到的租户上下文和资源作用域调用。

## 4. 第一版数据表

第一版新增四张表，其中两张属于租户模块，一张属于业务接入模块，一张用于租户与
业务动作关联。

### 4.1 `tenant.process_binding`

保存租户可以使用的审批流。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 主键 |
| tenant_id | UUID | 租户 ID，可关联 `tenant.tenant.id` |
| process_id | UUID | `process.approval_process.id`，不建立跨 Schema 外键 |
| status | VARCHAR(20) | `ENABLED`、`DISABLED` |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 最后更新时间 |

约束：

- `(tenant_id, process_id)` 唯一。
- 绑定停用后不能新发起审批，但不影响已经运行的审批实例。
- 绑定只表达使用权限，不保存流程版本、审批人或节点配置。

### 4.2 `tenant.process_usage_record`

保存某租户实际发起过某次审批的事实，也是按租户查询审批实例的作用域入口。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 使用记录 ID |
| tenant_id | UUID | 发起审批的租户 ID |
| process_id | UUID | 使用的稳定流程 ID |
| process_version_id | UUID | 发起时实际绑定的版本 ID |
| approval_instance_id | UUID | 对应的审批实例 ID |
| business_key | VARCHAR(200) | 业务系统中的原单据标识 |
| action_code | VARCHAR(100)，可空 | 审批通过后需要执行的业务动作 |
| created_at | TIMESTAMPTZ | 发起时间 |

约束：

- `approval_instance_id` 唯一，一次审批实例只属于一个租户。
- `(tenant_id, process_id, business_key)` 唯一，防止同一租户对同一业务单据重复创建
  审批实例。
- `process_id`、`process_version_id` 和 `approval_instance_id` 不建立跨 Schema 外键。
- 不重复保存审批状态、当前节点或耗时，这些数据统一从 `process` 运行表读取。

第一版只使用这一张表记录租户与审批实例之间的关系，不再建立含义重复的实例绑定表。

### 4.3 `integration.business_action`

定义审批通过后可以执行的一类业务动作以及它的参数要求。业务动作使用稳定的
`action_code`，与审批流相互独立，同一个动作可以被多条审批流使用。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 业务动作 ID |
| action_code | VARCHAR(100) | 全局唯一、稳定的业务动作标识 |
| name | VARCHAR(128) | 展示名称 |
| description | VARCHAR(500)，可空 | 动作说明 |
| http_method | VARCHAR(10) | 第一版支持 `POST`、`PUT`、`PATCH` |
| relative_path | VARCHAR(500) | 相对于租户 `callback_base_url` 的路径 |
| request_schema_json | JSONB | `execution_payload` 的 JSON Schema |
| success_status_codes_json | JSONB | 视为成功的 HTTP 状态码数组，默认全部 2xx |
| timeout_ms | INTEGER | 单次调用超时时间 |
| status | VARCHAR(20) | `ENABLED`、`DISABLED` |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 最后更新时间 |

第一版不单独建立参数规则表。参数规则直接保存在 `request_schema_json` 中，避免一份
JSON Schema 被拆成多条无必要的字段记录。

接口完整地址由以下两部分组成：

```text
tenant.tenant.callback_base_url + integration.business_action.relative_path
```

`relative_path` 必须以 `/` 开头，不能保存完整 URL，也不能包含由发起请求控制的主机
地址。这样可以避免业务请求绕过租户预先登记的回调地址。

### 4.4 `tenant.business_action_binding`

控制租户可以使用哪些业务动作。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 主键 |
| tenant_id | UUID | 租户 ID |
| business_action_id | UUID | `integration.business_action.id`，不建立跨 Schema 外键 |
| status | VARCHAR(20) | `ENABLED`、`DISABLED` |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 最后更新时间 |

约束 `(tenant_id, business_action_id)` 唯一。

第一版动作接口配置保存在 `integration.business_action`。不同租户通常通过不同的
`callback_base_url` 调用各自系统；如果同一动作在不同租户中需要不同相对路径，可以
创建不同的 `action_code`。路径覆盖等能力在确有需要时再加入绑定表。

## 5. 业务动作和审批流的关系

审批流本身不绑定固定业务动作。业务系统每次发起审批时传递 `action_code`：

- `action_code` 为空：只完成审批，不触发业务接口。
- `action_code` 非空：必须存在已启用的业务动作，并且当前租户已经绑定该动作。

这样，同一条付款审批流可以服务多个付款动作，也可以在只需要审批留痕时不执行任何
回调。流程定义不需要知道具体业务接口。

## 6. 发起审批接口

继续复用现有接口，不再增加第二个含义相同的发起入口：

```text
POST /api/processes/{process_id}/instances
X-API-Key: appr_live_xxx
```

请求示例：

```json
{
  "business_key": "PAY-20260921-001",
  "title": "供应商付款申请",
  "applicant_person_id": "人员UUID",
  "action_code": "PAYMENT_EXECUTE",
  "approval_form": {
    "amount": 10000,
    "supplier_name": "示例供应商",
    "reason": "采购付款"
  },
  "execution_payload": {
    "payment_id": "PAY-20260921-001",
    "amount": 10000
  }
}
```

成功响应继续返回审批实例 ID：

```json
{
  "instance_id": "审批实例UUID",
  "status": "RUNNING",
  "process_id": "审批流UUID",
  "process_version_id": "实际运行版本UUID",
  "process_version_no": 3,
  "current_node_name": "财务审批",
  "pending_approver_person_ids": ["人员UUID"],
  "idempotent_replay": false
}
```

## 7. 发起审批处理顺序

租户模式下按以下顺序处理：

1. 验证 `X-API-Key`，得到可信 `tenant_id`。
2. 确认租户处于 `ENABLED`，API Key 处于 `ACTIVE` 且没有过期。
3. 通过 `tenant.process_binding` 确认租户可以使用路径中的 `process_id`。
4. 查询流程当前已发布版本。
5. 使用流程版本的表单 Schema 校验 `approval_form`。
6. `action_code` 非空时，查询并校验当前租户可用的业务动作。
7. 使用业务动作的 `request_schema_json` 校验 `execution_payload`。
8. 根据 `tenant_id + process_id + business_key` 生成审批幂等键。
9. 创建审批实例并绑定当前已发布版本。
10. 推进 START 节点，直到进入人工审批节点或 END 节点。
11. 写入 `tenant.process_usage_record`。
12. 在同一个数据库事务中提交审批实例、首批任务和租户使用记录。

全局模式下，第 1、2、3、6 中的租户绑定校验以及第 11 步变为空操作；流程、表单、
业务动作和执行参数仍然正常校验。

## 8. 幂等和事务

### 8.1 幂等范围

租户模式的内部幂等键来源为：

```text
tenant_id + process_id + business_key
```

全局模式使用：

```text
global + process_id + business_key
```

相同幂等键且请求摘要一致时，返回原审批实例；请求摘要不一致时返回 `409`，避免修改
后的付款金额或执行参数被静默忽略。

### 8.2 事务边界

以下数据必须在同一个事务中成功或失败：

- `process.approval_instance`
- 首批 `process.approval_node_execution`
- 首批 `process.approval_task`
- `tenant.process_usage_record`

现有 `ApprovalInstanceService.start_instance()` 在内部提交事务。实现业务接入时需要把
“构造并推进实例”和“提交事务”拆开，由发起审批的应用服务统一提交。不能先提交审批
实例，再单独写租户使用记录，否则第二步失败会产生无法按租户查询的孤立实例。

并发提交相同业务单据时，由审批实例幂等约束和使用记录唯一约束共同兜底。冲突方回滚
后读取已有实例并返回幂等重放结果。

## 9. 租户作用域接入

租户模块新增资源注册：

```text
process.approval_process    → tenant.process_binding
integration.business_action → tenant.business_action_binding
process.approval_instance   → tenant.process_usage_record
```

发起接口通过 FastAPI 依赖获得业务接入上下文。一次请求只认证一次 API Key，上下文中
提供：

- 当前 `tenant_id`，全局模式下为空。
- 审批流资源作用域。
- 业务动作资源作用域。
- 审批实例使用记录写入能力。

业务服务只调用 `require_access()`、`apply_filter()` 和 `bind()`，不直接读取具体租户
绑定表。

## 10. 管理接口

管理接口继续使用临时 `X-Admin-Key`，后续替换为项目平台管理员身份。

### 10.1 租户审批流授权

```text
POST  /api/admin/tenants/{tenant_id}/process-bindings
GET   /api/admin/tenants/{tenant_id}/process-bindings
PATCH /api/admin/tenants/{tenant_id}/process-bindings/{binding_id}
```

创建绑定前必须通过 `ProcessService` 确认流程存在。PATCH 第一版只修改
`ENABLED`、`DISABLED`，不物理删除绑定记录。

### 10.2 业务动作管理

```text
POST  /api/admin/business-actions
GET   /api/admin/business-actions
GET   /api/admin/business-actions/{action_id}
PATCH /api/admin/business-actions/{action_id}
```

业务动作停用后不能用于新申请。已经完成审批并已经创建执行任务的请求由 callback
模块根据执行任务中的配置快照继续处理。

### 10.3 租户业务动作授权

```text
POST  /api/admin/tenants/{tenant_id}/business-action-bindings
GET   /api/admin/tenants/{tenant_id}/business-action-bindings
PATCH /api/admin/tenants/{tenant_id}/business-action-bindings/{binding_id}
```

### 10.4 租户审批使用记录

```text
GET /api/admin/tenants/{tenant_id}/process-usage-records
GET /api/admin/tenants/{tenant_id}/process-usage-records/{record_id}
```

列表支持按 `process_id`、`business_key`、`action_code` 和时间范围筛选。审批状态、当前
节点和耗时通过 `approval_instance_id` 批量查询 process 模块后组装，不写回使用记录。

## 11. 业务动作参数校验

业务动作的 `request_schema_json` 使用 JSON Schema，根类型必须是 `object`。发起审批
时对 `execution_payload` 执行校验，错误返回 `422` 和字段路径。

例如付款动作：

```json
{
  "type": "object",
  "required": ["payment_id", "amount"],
  "properties": {
    "payment_id": {
      "type": "string",
      "minLength": 1
    },
    "amount": {
      "type": "number",
      "exclusiveMinimum": 0
    }
  },
  "additionalProperties": false
}
```

审批通过后，callback 模块直接使用实例中保存的 `execution_payload_json` 作为请求体，
不从最新业务数据重新组装。审批实例 ID、业务单号、动作代码、回调幂等键和签名信息
通过标准请求头传递，避免污染业务请求参数。

## 12. 状态变化规则

- 流程绑定停用：阻止新申请，不影响运行中的实例。
- 动作绑定停用：阻止新申请使用该动作。
- 业务动作停用：阻止所有租户的新申请使用该动作。
- 租户停用或 API Key 撤销：新请求返回 `401` 或 `403`，已经运行的实例继续审批。
- 租户默认回调地址变化：只影响尚未创建回调执行任务的实例；callback 模块创建任务
  时会固化最终 URL 和动作配置。

## 13. 错误语义

| 场景 | HTTP 状态码 |
| --- | --- |
| 缺少、无效、过期或撤销的 API Key | 401 |
| 租户、流程绑定或动作绑定已停用 | 403 |
| 流程、业务动作不存在 | 404 |
| 同一业务单据使用不同内容重复发起 | 409 |
| 审批表单或执行参数校验失败 | 422 |
| 流程没有已发布版本或业务动作不可用 | 409 |

接口不向业务系统暴露其他租户是否绑定某个资源。无权使用时统一返回 403。

## 14. 第一版不做的能力

- 由业务系统动态传入完整回调 URL。
- 在发起请求中动态修改 HTTP 方法、相对路径、超时或成功状态码。
- 复杂字段映射和请求模板语言。
- OAuth、动态令牌交换和租户自定义认证插件。
- 一个审批实例执行多个业务动作。
- 审批进行中修改 `action_code` 或 `execution_payload`。
- 在业务接入模块中执行 HTTP 回调或重试。
- 按租户复制、修改审批流节点和审批人。

## 16. 开发顺序

1. 在 tenant 模块实现 `process_binding`、`process_usage_record` 和
   `business_action_binding`。
2. 注册审批流、业务动作和审批实例三种 TenantScope 资源定义。
3. 在 integration 模块实现 `business_action` 的模型、校验、Service 和管理接口。
4. 重构审批实例创建事务，使租户使用记录与审批运行数据原子提交。
5. 为发起审批接口接入业务上下文、流程授权和租户幂等范围。
6. 接入 `action_code` 授权及 `execution_payload` JSON Schema 校验。
7. 实现租户流程授权、动作授权和使用记录查询接口。
8. 补充租户模式、全局模式、幂等并发、绑定停用和参数错误测试。
9. 本模块验收后再设计 callback 执行任务和重试机制。

## 17. 验收标准

- 租户模式下，没有有效 API Key 不能发起审批。
- 租户不能使用未绑定或已停用的审批流。
- 租户不能使用未绑定或已停用的业务动作。
- `approval_form` 和 `execution_payload` 分别按对应 Schema 校验。
- 同一租户、流程和业务单据并发发起时只产生一个审批实例。
- 请求内容发生变化时返回 409，不静默复用旧实例。
- 审批实例和使用记录在同一事务中提交，不产生孤立数据。
- 可以通过租户和业务单号查到唯一审批实例及完整审批过程。
- `TENANCY_ENABLED=false` 时不依赖 tenant 表也能正常发起审批。
- 业务接入模块不执行外部 HTTP 请求。

## 18. 实现状态

本模块已按本文实现，接口清单和联调方式见同目录下的
[业务接入接口说明](./业务接入接口说明.md)。

### 18.1 数据表

`data/init.sql` 中新增四张表，都是可重复执行的建表语句，表和全部字段都带注释：

```text
tenant.process_binding            租户审批流授权，(tenant_id, process_id) 唯一
tenant.business_action_binding    租户业务动作授权，(tenant_id, business_action_id) 唯一
tenant.process_usage_record       审批使用记录，approval_instance_id 唯一，
                                  (tenant_id, process_id, business_key) 唯一
integration.business_action       业务动作定义，action_code 唯一
```

约束全部落到数据库：授权状态和动作状态有 `CHECK` 约束，动作 `http_method` 只允许
`POST`、`PUT`、`PATCH`，`relative_path` 由 `CHECK` 拒绝完整 URL 和协议相对地址。
只有 `tenant_id` 建立指向 `tenant.tenant.id` 的外键，`process_id`、
`business_action_id` 和 `approval_instance_id` 都不建立跨 Schema 外键。

`tenant.process_usage_record` 没有 `updated_at`：使用记录是历史事实，写入后不再修改，
也不提供修改和删除接口。

### 18.2 事务边界

`ApprovalInstanceService` 拆分为两个入口：

- `create_and_start_instance()`：校验、创建实例、推进流程，只执行 `add`、`flush` 和
  流程推进，不提交事务。
- `start_instance()`：在上述方法之后提交事务，供不需要扩大事务范围的调用方使用。

发起审批接口使用新的应用服务 `BusinessAccessService.start_approval()`，它在同一个
事务中写入 `approval_instance`、首批 `approval_node_execution`、
`approval_task` 和 `process_usage_record`，最后统一提交。使用记录冲突导致提交失败时
整体回滚，再按幂等键读取已经获胜的请求所创建的实例并返回重放结果。

### 18.3 租户作用域

`app/server/tenant/src/scope/tenant_scope.py` 新增三项资源注册：

```text
process.approval_process    → tenant.process_binding
integration.business_action → tenant.business_action_binding
process.approval_instance   → tenant.process_usage_record
```

使用记录类绑定没有启停状态，因此 `BindingDefinition` 增加 `status_field` 和
`required_attribute_fields`：前者为空表示记录存在即可访问，后者保证写入使用记录时
一定带上流程、版本和业务单据标识。

业务接入上下文由 `tenant/src/scope/business_access.py` 定义，FastAPI 通过
`use_business_access_context()` 获得。一个请求只认证一次 `X-API-Key`，三类资源作用域
共用同一次认证结果。全局模式下三类作用域都是空操作实现，不读写任何 tenant 表。

### 18.4 幂等范围

租户模式使用 `tenant_id + process_id + business_key`，全局模式使用
`global + process_id + business_key`。幂等键仍是 `approval_instance.idempotency_key`
的唯一约束，租户使用记录的唯一约束作为第二道防线同时兜住并发。

### 18.5 业务动作校验

- `action_code` 为空时不校验业务动作，`execution_payload` 可以为空。
- `action_code` 非空时依次确认动作存在、动作已启用、租户已经绑定该动作，最后按
  `request_schema_json` 校验 `execution_payload`。
- 请求参数 Schema 的根类型必须是 `object`，写入前先校验 Schema 本身合法。
- 执行参数错误返回 422，问题列表中带 `execution_payload` 前缀的完整字段路径。
- 全局模式下跳过第三步的租户绑定校验，其余校验不变。

### 18.6 管理接口的补充行为

- `POST /api/admin/tenants/{tenant_id}/process-bindings` 和业务动作授权接口都是幂等的：
  已经存在授权时返回原记录，授权处于停用时重新启用，不插入与唯一约束冲突的新行。
- 创建授权前通过 `ProcessService` 和 `BusinessActionService` 确认资源存在，租户模块
  不直接读取 process 和 integration 的表。
- 使用记录的运行状态通过 `ApprovalInstanceService.list_instance_overviews()` 批量读取
  process 运行表后组装，不写回使用记录。
