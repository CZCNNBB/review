# 业务执行子模块设计

> 状态：第一版已实现，实现说明见第 11 节  
> 适用范围：审批最终通过后的业务系统 HTTP 调用和执行结果展示

## 1. 模块目标

业务执行是 process 模块内部位于审批运行之后的最后阶段。审批中心只负责在审批最终通过后调用一次业务接口，
并如实记录本次调用的结果，供管理端和审批详情页面查看。

第一版不判断业务系统内部处理结果，不用回调结果反向修改审批结果，也不实现自动重试、
人工重试和业务补偿。

## 2. 触发规则

同时满足以下条件时创建执行记录：

1. 审批实例从 `RUNNING` 进入最终状态 `APPROVED`。
2. 审批实例的 `action_code` 不为空。
3. 当前审批实例尚未创建执行记录。

以下情况不创建执行记录：

- 最终状态为 `REJECTED` 或 `CANCELLED`。
- 审批仍处于 `RUNNING`。
- `action_code` 为空，表示该申请只需要完成审批。

`TENANCY_ENABLED=false` 时没有租户使用记录、回调基础地址和 Service Token，因此业务接入
接口收到非空 `action_code` 时必须在发起阶段直接拒绝。没有业务动作的纯审批申请仍可在
全局模式下正常运行。Worker 仍需把历史脏数据或绕过业务接入入口产生的缺少租户配置记录
更新为 `FAILED`，作为防御性处理。

审批推进和执行记录创建必须在同一个数据库事务中提交。实际 HTTP 请求只能在事务提交
后由后台执行器发出，不能占用审批事务。

### 2.1 审批运行如何进入业务执行

流程可能经过人工审批后结束，也允许使用 `START → END(APPROVED)` 在发起事务中直接
结束。因此，执行记录创建不能挂在 `ApprovalTaskService.handle_task()`，必须统一挂在
`ApprovalEngine.finish_instance()` 这个最终状态汇合点。

业务执行本身属于 process 模块，不再建立独立 callback Server，也不需要跨模块完成事件
端口。`ApprovalEngine` 通过构造函数接收同模块的 `BusinessExecutionService`，并在
`finish_instance()` 更新实例最终状态后调用它。该服务只在 `result_status=APPROVED` 且
`action_code` 不为空时添加 `PENDING` 记录；只写当前数据库 Session，不提交事务，也不
发送 HTTP 请求。

`approval_instance_id` 的唯一约束负责兜住重复创建。执行记录写入失败时，审批状态更新
也随当前事务一起回滚，避免出现审批已经提交但执行记录丢失的情况。单元测试可以给
`ApprovalEngine` 注入空实现或测试替身，保持推进引擎容易独立验证。

特别注意：`START → END(APPROVED)` 发生时，`tenant.process_usage_record` 可能尚未由外层
业务接入服务写入。因此业务执行服务不能在这里解析租户或发送请求，只能保存审批实例、
动作和参数信息。后台执行器必须等整个发起事务提交后，再通过使用记录取得租户配置。

## 3. 回调认证方案

### 3.1 确认方案：SERVICE_TOKEN

业务系统为审批中心创建一个服务账号，并通过自己现有的 Token 机制为该账号签发长期
有效的 Service Token。审批中心复用业务系统原有的认证请求头，不要求业务系统新增一套
审批中心专用认证协议。

示例：

```http
Authorization: Bearer service_token_xxx
```

不同租户可以配置不同的请求头名称和 Token 前缀：

```text
header_name = Authorization
token_prefix = Bearer

或者：

header_name = X-Token
token_prefix = 空字符串
```

业务系统的审计日志应将实际执行账号记录为“审批中心服务账号”。申请人、业务单号和
审批实例等业务身份继续从业务参数及审批数据中获取，不把自动执行伪装成用户本人操作。

### 3.2 两种凭据的方向

```text
业务系统 → 审批中心：租户 API Key
审批中心 → 业务系统：业务系统 Service Token
```

两种凭据不得共用。审批中心不保存和透传申请人的登录 Token，避免审批期间 Token
过期、撤销、权限变化和敏感凭据长期留存的问题。

### 3.3 凭据保存

Service Token 属于租户回调配置，继续放在 `tenant` 模块维护。现有
`tenant.tenant_callback_credential` 在业务执行子模块开发时从 HMAC 签名凭据调整为 Service
Token 凭据，至少保存：

| 字段 | 作用 |
| --- | --- |
| id | 凭据 ID |
| tenant_id | 所属租户 |
| name | 凭据用途名称 |
| header_name | 业务系统现有的认证请求头名称 |
| token_prefix | Token 前缀，例如 `Bearer`，允许为空 |
| token_ciphertext | 使用应用主密钥加密后的 Service Token |
| status | `ACTIVE`、`REVOKED` |
| expires_at | 可选过期时间 |
| created_at / revoked_at | 创建和撤销时间 |

一个租户同一时间只允许存在一个 `ACTIVE` 回调凭据。更换 Token 时在同一个数据库事务
中撤销旧凭据并写入新凭据，避免出现没有可用凭据或同时存在两个有效凭据的状态。

创建凭据接口由管理员输入 `name`、明文 `token`、`header_name`、`token_prefix` 和可选
`expires_at`。接口只在内存中接收明文并立即加密，响应不返回 Token 或密文，只返回凭据
元数据。创建新凭据时自动撤销原有 `ACTIVE` 凭据，不要求管理员先单独撤销；数据库使用
`WHERE status = 'ACTIVE'` 的部分唯一索引兜住同一租户最多一条有效凭据的并发边界。

Token 使用已有 `APPROVAL_CREDENTIAL_MASTER_KEY` 和 Fernet 能力加密保存。Token 明文
不写入执行记录、响应体和应用日志，查询接口只返回凭据元数据。

当 `BUSINESS_EXECUTION_WORKER_ENABLED=true` 时，应用启动必须校验
`APPROVAL_CREDENTIAL_MASTER_KEY` 已配置且可以初始化 Fernet；缺失或格式错误时启动失败并
给出明确提示。`APPROVAL_ADMIN_KEY` 不属于 Worker 启动条件，只影响管理接口鉴权。

### 3.4 暂不采用的方案

| 方案 | 第一版不采用的原因 |
| --- | --- |
| 透传用户 Token | 审批是异步过程，用户 Token 可能过期、撤销或发生权限变化 |
| HMAC 请求签名 | 安全性更强，但要求业务系统新增验签协议和时间戳、防重放处理 |
| OAuth Client Credentials | 标准化程度高，但要求各业务系统提供授权服务器或机器身份流程 |
| mTLS | 身份强度高，但证书签发、部署、轮换和网关配置成本较高 |

后续安全等级提高时，可以在不改变执行记录模型的前提下增加新的认证类型。

## 4. 回调地址和请求内容

`integration.business_action` 是预先配置好的业务动作执行器定义。审批申请传入的
`action_code` 是查找该配置的稳定唯一标识。第一版所有业务动作统一交给 process 模块内的
通用 HTTP 执行器处理，不为每个 `action_code` 编写单独的 Python 执行器，也暂不增加
`executor_type`。管理员新增或调整业务动作时，只需维护数据库配置，不需要发布后端代码。

```text
approval_instance.action_code
    → integration.business_action
    → process 通用 HTTP 执行器
```

查找到业务动作后，系统从中取得 HTTP 方法、相对路径、超时时间、成功状态码规则和参数
Schema。租户配置只补充本租户的基础地址和 Service Token，不重新定义业务动作。

process 模块不得直接导入 tenant Repository 或 Service。`app/common` 增加
`CallbackTargetResolver` 端口，按 `approval_instance_id` 解析并返回只读的
`CallbackTarget`，其中包含 `tenant_id`、基础地址、请求头名称、Token 前缀和已解密 Token。
tenant 模块在 `tenant/src/scope/` 提供实现，应用层负责装配；process 只依赖端口抽象。

完整地址由以下两部分拼接：

```text
tenant.callback_base_url + integration.business_action.relative_path
```

请求方法、超时和成功状态码来自 `integration.business_action`。请求体使用审批实例中已经
保存的 `execution_payload_json`，业务系统需要的申请人和业务审计信息由业务方在发起
审批时放入该参数，审批中心不保存用户 Token，也不动态伪造用户身份。

## 5. 数据表

第一版在 process Schema 中增加一张表：

```text
process.business_execution_record
```

一条记录既表示待执行任务，也保存唯一一次 HTTP 调用结果。第一版没有多次重试，因此
不拆分 `execution_job` 和 `execution_attempt`。

| 字段 | 作用 |
| --- | --- |
| id | 执行记录 ID，同时作为稳定执行标识 |
| approval_instance_id | 审批实例 ID，全局唯一，外键关联 process.approval_instance |
| business_action_id | 实际使用的业务动作 ID，不建立跨 Schema 外键；配置异常时允许为空 |
| action_code | 业务动作标识快照 |
| request_url | `VARCHAR(1000)`，实际请求地址快照，创建记录时允许为空，由 Worker 补齐 |
| http_method | 实际 HTTP 方法快照，配置异常时允许为空 |
| relative_path | 业务动作相对路径快照，配置异常时允许为空 |
| success_status_codes_json | 成功状态码规则快照，配置异常时允许为空 |
| timeout_ms | HTTP 超时时间快照，配置异常时允许为空 |
| request_payload_json | 实际发送参数快照 |
| status | `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED` |
| http_status_code | HTTP 响应状态码，未取得响应时为空 |
| response_body | `TEXT`，响应内容，按 UTF-8 截断到 8192 字节 |
| error_message | `VARCHAR(1000)`，网络异常、超时或配置错误摘要，超出时截断 |
| started_at / finished_at | 实际调用开始和结束时间 |
| created_at / updated_at | 创建和最后更新时间 |

第一版不单独保存 `duration_ms`。查询时使用 `finished_at - started_at` 计算耗时，避免时间字段
和耗时字段之间出现不一致。

业务执行表不保存 `tenant_id`，也不建立指向 `tenant` Schema 的外键。执行器通过
`approval_instance_id` 和现有 `tenant.process_usage_record` 找到实例所属租户，再读取
租户地址和 Service Token。这样关闭租户能力后，审批运行模块仍然可以独立工作。

业务执行服务可以在同一事务中通过 `action_code` 读取业务动作，并把动作 ID、方法、相对
路径、成功状态码和超时保存成执行快照。`request_url` 在后台执行器取得租户基础地址后
再补齐。这样执行记录等待期间即使业务动作配置被修改，也不会改变本次已经批准的调用
方式。

动作停用只阻止新申请。运行中的审批结束时应按 `action_code` 读取动作配置，不应因为动作
后来变为 `DISABLED` 而阻止原审批结束。如果动作配置确实不存在，审批仍然正常通过并创建
快照字段为空的 `PENDING` 记录，Worker 随后将其更新为 `FAILED`，错误原因为“业务动作配置
缺失”；不能让配置缺失导致审批事务永久无法完成。

## 6. 状态流转

```text
PENDING → RUNNING → SUCCEEDED
                  → FAILED
```

- `PENDING`：审批已通过，等待后台执行器处理。
- `RUNNING`：执行器已经领取任务，准备或正在发送请求。
- `SUCCEEDED`：HTTP 状态码符合业务动作配置的成功状态码；配置为空时全部 2xx 成功。
- `FAILED`：配置缺失、Token 不可用、网络异常、超时或 HTTP 状态码不符合成功规则。

业务执行状态不会修改已经确定的审批状态。审批保持 `APPROVED`，页面分别展示审批结果和
业务执行结果。

## 7. 执行过程

1. 审批引擎将实例推进为 `APPROVED`，并在 `finish_instance()` 调用业务执行服务。
2. 业务执行服务使用实例的 `action_code` 查找 `integration.business_action`，在同一事务内按
   `approval_instance_id` 创建唯一的 `PENDING` 执行记录，并保存业务动作配置快照。
3. 事务提交后，后台执行器领取该记录并更新为 `RUNNING`。
4. 通过审批使用记录取得租户，再读取租户回调地址和唯一有效的 Service Token。
5. 使用执行记录中的动作配置快照，并与租户基础地址拼接最终请求地址。
6. 解密 Token，只在内存中构造认证请求头。
7. 使用审批实例的 `execution_payload_json` 发送 HTTP 请求。
8. 保存状态码、截断后的响应内容、错误、开始时间和结束时间；查询时计算耗时。
9. 根据成功状态码将记录更新为 `SUCCEEDED` 或 `FAILED`。

现有项目使用 psycopg2 和同步 SQLAlchemy Session，因此第一版 Worker 采用同步线程模型，
不能使用 asyncio 协程直接调用同步 ORM。FastAPI `lifespan` 只负责启动和停止一个后台
`threading.Thread`；协调线程使用同步 Session 领取任务，再交给
`ThreadPoolExecutor(max_workers=BUSINESS_EXECUTION_CONCURRENCY)` 执行。每个执行任务使用
独立 Session，Session 不得在线程之间共享；Worker 持有一个可在线程间共享的同步
`httpx.Client` 复用连接池，并在所有执行线程结束后统一关闭。后续调用量增大后可以在不
改变表结构的前提下迁移为独立 Worker 进程。

后台线程使用 `threading.Event.wait()` 等待轮询间隔，使应用关闭时可以立即唤醒并停止，
不要使用无法及时中断的固定 `sleep()`。关闭流程先停止领取新任务，等待当前进程已经领取为
`RUNNING` 的任务完成 HTTP 调用并保存为 `SUCCEEDED` 或 `FAILED`，最后关闭线程池和 HTTP
Client。尚未领取的记录保持 `PENDING`，留给服务下次启动后处理。第一版只消费 `PENDING`
记录，不自动重新执行 `FAILED` 记录。

正常的 FastAPI lifespan 关闭不设置内部等待上限。部署在 systemd、容器或 Kubernetes 时，
外部停止宽限期应大于业务动作允许的最大 HTTP 超时时间，并额外预留保存数据库结果的时间；
如果外部环境在宽限期结束后强制杀死进程，应用无法继续保证在途结果完成落库。

### 7.1 Worker 环境配置

后台 Worker 的运行参数必须通过环境变量配置，不能把轮询频率和领取数量写死在代码中。
第一版使用以下配置：

| 环境变量 | 默认值 | 作用 |
| --- | --- | --- |
| `BUSINESS_EXECUTION_WORKER_ENABLED` | `true` | 是否在当前应用进程中启动业务执行 Worker |
| `BUSINESS_EXECUTION_POLL_INTERVAL_SECONDS` | `2` | 没有可执行任务时，两次查询之间的等待秒数 |
| `BUSINESS_EXECUTION_BATCH_SIZE` | `10` | 每次最多领取的 `PENDING` 记录数量 |
| `BUSINESS_EXECUTION_CONCURRENCY` | `5` | 当前应用进程内同时执行的最大 HTTP 请求数量 |

配置读取时需要校验：轮询间隔必须大于 `0`，批量数量和并发数必须是正整数。并发数不能
超过批量领取数量，配置不合法时应用启动失败并给出明确错误，不能在运行时静默修正。

Worker 每轮按以下方式运行：

```text
单轮计划处理最多 BUSINESS_EXECUTION_BATCH_SIZE 条记录
    → 每波领取最多 min(本轮剩余数量, BUSINESS_EXECUTION_CONCURRENCY) 条 PENDING 记录
    → 提交本波领取事务
    → 并发执行本波任务并等待完成
    → 未达到单轮批量上限且未收到停机信号时，再领取下一波
    → 本轮处理完成
    → 没有新任务时等待 BUSINESS_EXECUTION_POLL_INTERVAL_SECONDS
```

`BUSINESS_EXECUTION_WORKER_ENABLED=false` 时，审批通过仍然正常创建 `PENDING` 记录，但
当前应用进程不会领取任务，适用于只提供 API 的进程或后续部署独立 Worker 的场景。多个
应用进程同时启用 Worker 时，PostgreSQL 的 `FOR UPDATE SKIP LOCKED` 保证一条任务只被一个
进程领取。需要注意，总并发量约等于应用进程数乘以单进程并发配置。

领取事务只负责锁定 `PENDING`、更新为 `RUNNING` 和提交。事务提交后才能发送 HTTP 请求，
不能在持有行锁时等待外部系统。并发任务各自创建和关闭数据库 Session；最终状态更新应
附带 `status = 'RUNNING'` 条件，防止意外覆盖已经变化的状态。

实际领取数量不得超过当前进程的并发槽位，避免记录已被标记为 `RUNNING`，实际却仍在线程池
队列中等待。停机信号与领取事务通过进程内锁确定先后顺序：停机开始后不再提交新的领取事务，
停机开始前已经提交为 `RUNNING` 的任务全部等待执行完成。

第一版采用“尽力调用一次”的交付语义，不宣称分布式意义上的 exactly-once。执行器发送
请求期间如果进程异常退出，记录可能停留在 `RUNNING`，由管理页面展示并交给后台人员
核对；第一版不自动重新发送，避免在结果不明确时重复执行业务动作。

## 8. 查询与展示

第一版提供管理端查询能力：

```text
GET /api/admin/execution-records
GET /api/admin/execution-records/{record_id}
```

两个接口统一复用 `verify_admin_key`，通过 `APPROVAL_ADMIN_KEY` 鉴权；未配置管理密钥时
沿用现有管理接口行为返回 `503`。

列表支持按审批实例、业务动作和执行状态筛选。审批详情可以通过
`approval_instance_id` 关联展示执行状态、HTTP 状态码、错误摘要和耗时。

响应中不得包含 Service Token、加密密文或完整认证请求头。响应正文写库前按 UTF-8 安全
截断到 8192 字节，不能截断在多字节字符中间，避免业务系统返回大对象导致数据库和管理
页面负担过重。

## 9. 第一版明确不做

- 自动重试和人工重试。
- 多次执行尝试明细。
- 业务执行失败后的业务补偿。
- 根据响应 JSON 判断业务是否真正成功。
- 使用业务执行结果反向修改审批状态。
- 保存或透传用户登录 Token。
- HMAC、OAuth Client Credentials 和 mTLS。

## 10. 验收标准

- 只有最终审批通过且配置了 `action_code` 的实例产生执行记录。
- 同一审批实例最多产生一条执行记录。
- 实际 HTTP 请求发生在审批事务提交之后。
- 业务执行请求使用租户配置的现有认证请求头和 Service Token。
- Token 只以密文落库，不出现在日志、执行记录和查询响应中。
- 成功、HTTP 失败、网络异常、超时和配置缺失都能形成可查询记录。
- 业务执行失败不改变审批实例的 `APPROVED` 状态。
- 租户关闭或凭据撤销后不再发出新的请求，并记录明确失败原因。

## 11. 实现状态

本模块已按本文实现，关键落点如下。

### 11.1 数据表

```text
process.business_execution_record    执行记录，approval_instance_id 唯一，
                                     status 由 CHECK 约束限制为四个取值
tenant.tenant_callback_credential    升级为 Service Token 结构，
                                     部分唯一索引保证一个租户最多一条 ACTIVE 记录
```

执行表不保存 `tenant_id`，也不建立指向 `tenant` Schema 的外键，只有
`approval_instance_id` 建立指向 `process.approval_instance` 的外键。`response_body` 保存时
截断到 8 KB，`error_message` 截断到 1000 字符，耗时统一由 `finished_at - started_at` 计算，
不保存 `duration_ms`。

早期 HMAC 凭据结构到 Service Token 结构的一次性升级脚本见
`data/migrations/20260922_callback_credential_service_token.sql`，发现 `ACTIVE` 凭据时会主动中止。

### 11.2 创建入口

`ApprovalEngine.finish_instance()` 是实例进入最终状态的唯一汇合点，人工审批推进和
`START → END(APPROVED)` 都会经过这里。引擎通过构造函数接收同模块的
`BusinessExecutionService`，由它在同一个 Session 中创建 `PENDING` 记录并固化动作配置快照；
只 `add`，不 `commit`，不发送 HTTP 请求。

业务动作在审批期间被删除时记录照常创建、快照留空，由执行器判为配置缺失失败，避免让已经
完成的审批事务回滚导致这条审批永远无法通过。

### 11.3 后台 Worker

Worker 在独立后台线程中运行（见第 11.6 节），通过 `FOR UPDATE SKIP LOCKED` 领取 `PENDING`
记录，领取事务提交后才发出请求，HTTP 期间不持有任何数据库会话和行锁。每次领取、每次结果
保存都使用独立 Session。

### 11.4 通用执行器

`process/src/execution/executor.py` 是唯一的业务动作执行器，方法、相对路径、超时和成功
状态码全部来自记录中的配置快照，新增业务动作不需要修改后端代码。响应正文流式读取并在达到
上限时提前停止，避免为了保存几 KB 结果把巨大响应读进内存。

### 11.5 跨模块边界

业务执行位于 `process`，但回调地址和 Service Token 属于 `tenant`。`app/common/scope/`
新增 `CallbackTargetResolver` 端口，`tenant/src/scope/callback_config.py` 提供实现并通过
`create_callback_target_resolver()` 按租户开关装配。`process` 只依赖端口，不查询任何
`tenant` 表，也不导入 `tenant` 的 Repository。

全局模式（`TENANCY_ENABLED=false`）没有租户归属，无法解析回调目标，因此发起审批时直接
拒绝带 `action_code` 的请求并返回 409，不让申请进入注定失败的链路。

### 11.6 并发模型

Worker 使用后台线程而不是 asyncio 协程。整个后端使用同步的 `SQLModel Session`（psycopg2），
在协程里查询数据库会阻塞 FastAPI 事件循环并让 API 服务停摆，因此领取循环在自己的线程中
运行，单批任务提交给 `ThreadPoolExecutor(max_workers=BUSINESS_EXECUTION_CONCURRENCY)`，
每个线程使用独立 Session 和共享的同步 `httpx.Client`。后台协调线程设为守护线程，只用于
进程被强制终止时的最后兜底；正常 lifespan 关闭会等待所有在途任务完成。

### 11.7 查询接口

```text
GET /api/admin/execution-records                列表，可按审批实例、动作和状态筛选
GET /api/admin/execution-records/{record_id}    详情，附带请求参数和响应正文
```

两个接口都要求 `X-Admin-Key`，响应不包含 Service Token、密文和完整认证请求头。
