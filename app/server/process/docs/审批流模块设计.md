# 审批流定义模块设计

> 设计状态：显式版本方案已确认并完成定义层代码改造。

## 1. 模块目标

审批流定义模块负责节点能力、流程身份、流程版本、版本节点和流程编排的维护。

业务系统发起审批时只传稳定的 `process_id`。审批中心自动选择当前已发布版本，业务系统和审批人不需要选择版本。

完整的审批实例、节点执行、任务和运行记录方案见同目录下的 `审批流运行模块设计.md`。

## 2. 已确认的设计原则

1. 节点定义、流程、流程版本和版本节点都使用 UUID `id`。
2. 节点定义描述系统支持的公共节点能力，它的内容由代码里的类型清单决定，不由管理端维护。
3. 版本节点描述某个流程版本中的具体节点配置。
4. 流程版本保存表单、节点、连线和分支条件。
5. 草稿版本可以编辑，已发布版本永久只读。
6. 发布新版本不影响绑定旧版本的审批实例。
7. 审批模式和审批人保存在版本节点 `config_json` 中。
8. 节点关系和分支规则保存在版本 `orchestration_json` 中。
9. 分支由独立的「条件分支」节点表达，普通节点只能有一条出线。
10. 多人审批只支持 `AND` 和 `OR`，不支持顺序审批。
11. 租户只决定能否使用流程，不覆盖版本、节点和审批人配置。

## 3. 核心表

```text
process.node_definition
process.approval_process
process.approval_process_version
process.approval_process_version_node
tenant.process_binding
```

关系如下：

```text
process.approval_process
        │ 1:N
        ▼
process.approval_process_version
        │ 1:N
        ▼
process.approval_process_version_node
        │ N:1
        ▼
process.node_definition

tenant.process_binding ── process_id ──► process.approval_process
```

租户绑定属于 `tenant` Schema，其余定义表属于 `process` Schema。

## 4. `process.node_definition`

节点能力定义描述后端已经支持的执行类型和前端配置契约，不保存某个版本中的具体审批人或画布位置。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 节点能力定义 ID，内置类型用清单里写死的固定 UUID |
| node_type | VARCHAR(32) | `START`、`APPROVAL`、`CONDITION`、`END` |
| name | VARCHAR(100) | 节点面板展示名称，全局唯一 |
| description | VARCHAR(500) | 节点能力说明 |
| icon | VARCHAR(100) | 前端图标标识 |
| config_schema_json | JSONB | 版本节点允许配置的字段规则 |
| ui_schema_json | JSONB | 节点配置面板展示规则 |
| status | VARCHAR(20) | `ENABLED`、`DISABLED` |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

这张表是代码清单的副本：清单在 `src/node_catalog.py`，应用启动时由
`service/node_definition_sync.py` 同步（按 `node_type` 找到已有行就地更新、代码里没有的类型
停用）。因此内置类型一类一行，`node_type` 既是执行器分类也是同步的匹配键。

```python
NODE_HANDLERS = {
    "START": StartNodeHandler(),
    "APPROVAL": ApprovalNodeHandler(),
    "CONDITION": ConditionNodeHandler(),
    "END": EndNodeHandler(),
}
```

版本发布时把 `node_type` 固化到版本节点中。运行时只读取版本节点，不依赖后来变化的节点定义。

节点定义不物理删除：代码里去掉一种类型时同步只把它停用，历史版本节点仍然引用着这一行。
改配置 Schema 改的是清单，只影响之后保存/发布的草稿 —— 草稿重新校验时按新规则，已经发布的
版本按发布时固化的版本节点运行，不受影响。

## 5. `process.approval_process`

审批流主体只保存稳定身份和当前生效版本。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 稳定的 `process_id` |
| name | VARCHAR(128) | 当前展示名称 |
| description | VARCHAR(500) | 当前说明 |
| status | VARCHAR(20) | `DRAFT`、`ENABLED`、`DISABLED` |
| current_version_id | UUID，可空 | 当前已发布版本 ID |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

流程不物理删除。停用流程只阻止创建新审批实例，不影响已有版本和运行实例。

## 6. `process.approval_process_version`

流程版本保存一份完整流程中的主体、表单和编排关系。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 版本 ID |
| process_id | UUID | 所属流程 ID |
| version_no | INTEGER | 从 1 开始递增 |
| status | VARCHAR(20) | `DRAFT`、`PUBLISHED` |
| name | VARCHAR(128) | 版本内流程名称 |
| description | VARCHAR(500) | 版本内流程说明 |
| form_schema_json | JSONB | 审批表单规则 |
| form_ui_schema_json | JSONB | 表单展示规则 |
| orchestration_json | JSONB | 节点连线、条件和默认路径 |
| revision | INTEGER | 草稿并发保存修订号 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |
| published_at | TIMESTAMPTZ，可空 | 发布时间 |

约束：

- `(process_id, version_no)` 唯一。
- 同一流程同时最多存在一个草稿版本。
- 已发布版本不可修改或删除。
- 草稿每次保存后 `revision` 加一。

## 7. `process.approval_process_version_node`

版本节点保存该版本画布中的具体节点。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 当前版本中的节点 ID |
| process_version_id | UUID | 所属版本 ID |
| node_definition_id | UUID | 来源节点能力定义 ID |
| node_type | VARCHAR(32) | 发布时固化的执行类型 |
| name | VARCHAR(128) | 当前版本中的节点名称 |
| config_json | JSONB | 审批模式、审批人等配置 |
| position_json | JSONB | 画布坐标 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

`process_version_id` 和 `node_definition_id` 都建立 `process` Schema 内的数据库外键。

审批节点配置示例：

```json
{
  "approval_mode": "AND",
  "approvers": [
    {"person_id": "人员A的UUID"},
    {"person_id": "人员B的UUID"}
  ]
}
```

人员 ID 不建立指向 `organization` Schema 的跨 Schema 外键，由流程服务在草稿保存和发布前校验。

版本主体和版本节点明确分表，不把全部节点塞进版本表的一个大 JSON。这样可以直接按
`process_version_id` 查询、校验和索引节点，也能用数据库外键约束节点所属版本和节点
定义。后续增加节点执行统计或排查单个节点配置时，不需要读取并改写整份节点数组。
代价是保存整图时需要同时维护两张表，因此 Service 必须在同一个事务中保存版本主体、
版本节点和编排关系。

## 8. `tenant.process_binding`

租户流程绑定只负责判断某个租户能否使用某条流程。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 绑定 ID |
| tenant_id | UUID | 租户 ID |
| process_id | UUID | 可以使用的流程 ID |
| status | VARCHAR(20) | `ENABLED`、`DISABLED` |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

约束和边界：

- `(tenant_id, process_id)` 唯一。
- 不保存流程版本覆盖配置。
- 不保存审批人覆盖配置。
- 发起审批时只校验流程绑定，实际使用版本由 `current_version_id` 决定。

## 9. 节点类型

### 9.1 START

- 每个版本必须且只能有一个 START。
- START 不能作为连线目标。
- START 不产生人工任务，完成后立即推进。

### 9.2 APPROVAL

- 必须配置 `AND` 或 `OR`。
- 必须至少配置一名有效审批人。
- 进入节点时同时创建全部审批任务。
- 任意一人拒绝后审批实例立即拒绝。
- 只能有一条出线：审批通过后去哪，分流交给条件分支节点。

### 9.3 CONDITION

- 进入节点后立即按出线条件选择后续节点，不产生人工待办、不中断实例。
- 出线按顺序构成一条 if/elif/else 阶梯：除最后一条外每条都要有条件，最后一条是
  「其余情况」，不能带条件，用来兜住所有条件都不满足的情况。
- 分支可以只定义条件、先不接去向（`target_node_id` 为空），补齐前由
  `BRANCH_TARGET_REQUIRED` 拦下，可以边配条件边接线。
- 至少需要一条出线（否则等同于流程断在这里）。
- 分流只允许从这个类型出去；其他类型出现多条出线或带条件的出线都会被校验拦下
  （`TOO_MANY_OUTGOING_CONNECTIONS`）。

### 9.4 END

- 每个版本至少有一个 END。
- END 不能作为连线来源。
- 没有配置项：走到 END 就是审批通过、流程完成。审批被拒绝时实例在人工审批节点当场
  结束，不会走到 END，所以不存在"拒绝出口"。

## 10. 多人审批

AND：

- 所有人同意后节点通过。
- 任意一人拒绝后实例立即拒绝。
- 拒绝后其他待办自动取消。

OR：

- 任意一人同意后节点通过。
- 任意一人拒绝后实例立即拒绝。
- 第一个成功提交的有效结果决定节点结果。
- 节点形成结果后其他待办自动取消。

运行模块通过数据库事务和实例行锁保证并发操作只形成一个最终结果。

## 11. 流程编排

节点连线和条件保存在版本的 `orchestration_json` 中，不建立独立连线表。

```json
{
  "connections": [
    {
      "source_node_id": "开始节点UUID",
      "target_node_id": "财务审批节点UUID"
    },
    {
      "source_node_id": "条件分支节点UUID",
      "target_node_id": "负责人审批节点UUID",
      "condition": {
        "field": "approval_form.amount",
        "operator": "GT",
        "value": 10000
      }
    },
    {
      "source_node_id": "条件分支节点UUID",
      "target_node_id": "结束节点UUID"
    }
  ]
}
```

条件只能挂在条件分支节点的出线上（普通节点不允许带条件的出线）。分支可以先在节点里定义好条件、
之后再拉线到目标节点，此时 `target_node_id` 为 `null`；这是一个合法的中间状态，发布前的校验要求补齐。

条件分支节点的出线按数组顺序构成 if/elif/else 阶梯：运行时从上往下选择第一条命中的条件路径，
全部未命中时走最后一条（「其余情况」）。兜底路径的位置由顺序决定，不再使用单独的 default 标志位——
旧版本写入的 default 字段会被忽略，不影响校验和运行。

第一版条件只支持结构化 JSON：

```text
EQ、NE、GT、GTE、LT、LTE、IN、NOT_IN、IS_EMPTY、NOT_EMPTY
```

## 12. 草稿保存与并发控制

前端整图保存请求携带版本 ID 和修订号：

```json
{
  "version_id": "版本UUID",
  "revision": 5,
  "name": "付款审批流程",
  "form_schema": {},
  "form_ui_schema": {},
  "nodes": [],
  "orchestration": {"connections": []}
}
```

后端在一个事务中：

1. 校验目标版本仍为草稿。
2. 校验数据库中的 `revision` 与请求一致。
3. 批量校验节点定义和审批人。
4. 增删改当前版本节点。
5. 保存表单和编排。
6. 将 `revision` 加一。

修订号不一致时返回 409，前端重新加载，防止两个人同时编辑造成静默覆盖。

## 13. 完整性校验

草稿保存和发布时至少校验：

- 版本节点 ID 唯一。
- 节点定义存在且可用。
- 节点配置符合节点定义 Schema。
- 审批人存在、启用且没有重复。
- 恰好一个 START，至少一个 END。
- 连线两端属于当前版本。
- START 不作为目标，END 不作为来源。
- 全部节点从 START 可达。
- 非 END 节点存在后续连线。
- 不存在环。
- 存在条件连线时具有唯一默认路径。
- 条件字段和操作符与表单 Schema 匹配。
- 至少存在一个 `APPROVED` 结束节点。

## 14. 版本生命周期

新建流程时创建 V1 草稿。首次发布后，V1 变为只读并成为当前版本。

再次编辑时：

1. 复制当前发布版本形成 V2 草稿。
2. 为节点生成新的 UUID。
3. 重写编排中的节点 UUID。
4. V2 编辑期间，新实例继续使用 V1。
5. V2 发布成功后，原子切换 `current_version_id`。

同一流程可以长期保留多个发布版本，但只能有一个当前版本和一个编辑中的草稿。

## 16. 第一版边界

第一版不实现：

- 用户手动选择历史版本发起审批。
- 同时维护多个草稿版本。
- 顺序审批。
- 图级并行分支和汇聚。
- 任意脚本条件。
- 退回重审、加签、转交和委托。
- 动态部门负责人或表达式选人。
- 子流程和定时器节点。

节点内部多人任务仍然同时创建；这里不支持的是两条流程路径同时运行。
