# 审批流模块设计

> 设计状态：第一版方案已确认，下一步按本方案实现。

## 1. 模块目标

审批流模块负责在管理页面中创建、编辑、校验、复制和启停审批流程。业务系统发起审批时明确传入 `process_id`，审批中心读取当前流程定义并创建不可变的运行快照。

第一版不提供显式流程版本管理。管理员编辑的是流程当前定义，修改只影响之后新发起的审批实例。

## 2. 已确认的设计原则

1. 所有节点定义、流程和节点实例都使用 UUID `id` 作为唯一标识，不增加业务 `code`。
2. 节点定义描述“系统支持什么能力”。
3. 节点实例描述“这个具体节点怎么执行”。
4. 流程主体描述“节点如何连接、何时分支”。
5. 审批表单直接保存在流程主体 JSONB 字段中。
6. 审批模式和审批人直接保存在节点实例 `config_json` 中。
7. 节点关系和分支规则统一保存在流程主体 `orchestration_json` 中。
8. 分支属于流程编排能力，不建立 `BRANCH` 节点定义。
9. 多人审批任务同时创建，只支持 `AND` 和 `OR`，不支持顺序审批。
10. 租户只决定能否使用流程，不覆盖流程节点和审批人配置。
11. 审批发起时保存流程快照，运行中的实例不读取后来变化的流程定义。

## 3. 四张核心表

审批流定义和租户授权共使用四张表：

```text
process.node_definition
process.approval_process
process.approval_process_node
tenant.process_binding
```

其中前三张属于 `process` Schema，租户授权表属于 `tenant` Schema。所有初始化结构统一维护在 `backend/data/init.sql`。

```text
process.node_definition
        ↑ node_definition_id
process.approval_process_node
        ↑ process_id
process.approval_process
        ↑ process_id
tenant.process_binding
```

## 4. process.node_definition

节点能力定义表用于描述系统支持的节点功能和前端配置契约，不保存某条流程中的具体节点、审批人或位置。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 节点能力定义唯一标识 |
| node_type | VARCHAR(32) | 后端执行类型：START、APPROVAL、END |
| name | VARCHAR(100) | 节点面板展示名称 |
| description | VARCHAR(500) | 节点能力说明 |
| icon | VARCHAR(100) | 前端图标标识 |
| config_schema_json | JSONB | 节点实例允许配置的字段规则 |
| ui_schema_json | JSONB | 节点配置面板展示规则 |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

`id` 是节点定义的唯一标识。`node_type` 只表示后端执行分类，不承担唯一标识作用。多个节点定义可以使用相同的 `node_type`，但拥有不同的名称、图标和配置 Schema。

节点实例通过 `node_definition_id` 引用节点定义。后端读取节点定义的 `node_type` 后，从执行器注册表选择对应执行器：

```python
NODE_HANDLERS = {
    "START": StartNodeHandler(),
    "APPROVAL": ApprovalNodeHandler(),
    "END": EndNodeHandler(),
}
```

`node_definition` 保存的是能力元数据，真正的 Python 执行逻辑仍由后端实现。新增节点定义时，`node_type` 必须是后端已经支持的类型。

节点定义被流程引用后不物理删除，只允许停用。停用后不能继续向流程添加该节点，引用它的流程也不能重新启用。

## 5. process.approval_process

流程主体表代表一条完整审批流，同时保存审批表单和流程编排。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 稳定的 `process_id` |
| name | VARCHAR(128) | 流程名称 |
| description | VARCHAR(500) | 流程说明 |
| status | VARCHAR(20) | DRAFT、ENABLED、DISABLED |
| form_schema_json | JSONB | 审批表单字段、类型、必填和校验规则 |
| form_ui_schema_json | JSONB | 表单标签、顺序、分组和展示组件 |
| orchestration_json | JSONB | 节点关系、分支条件和默认路径 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

业务系统发起审批时传入该表的 `id`。流程不提供物理删除，废弃流程设置为 `DISABLED`。

表单与流程是一对一关系，并且总是跟随流程一起创建、修改、复制和生成快照，因此不单独建立表。

## 6. process.approval_process_node

流程节点实例表保存画布中的每一个具体节点。节点只关心自身能力和配置，不保存下一个节点或分支条件。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 节点实例唯一标识 |
| process_id | UUID | 所属流程 ID |
| node_definition_id | UUID | 节点能力定义 ID |
| name | VARCHAR(128) | 当前节点实例名称 |
| config_json | JSONB | 当前节点实例的全部功能配置 |
| position_json | JSONB | 前端画布坐标 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

`process_id` 和 `node_definition_id` 都建立同一 `process` Schema 内的数据库外键。

前端每次把节点定义拖入画布时立即生成节点 UUID，因此同一次完整流程保存请求可以直接在 `orchestration_json` 中引用新节点。

审批节点配置示例：

```json
{
  "approval_mode": "AND",
  "approvers": [
    {"person_id": "人员A的UUID"},
    {"person_id": "人员B的UUID"}
  ]
}
```

审批人是节点实例配置的一部分，不单独建立审批人表。人员 ID 不建立指向 `organization` Schema 的跨 Schema 外键，由流程服务在保存和启用前校验。

## 7. tenant.process_binding

租户流程绑定表只负责判断某个租户能否使用某个流程。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 绑定记录主键 |
| tenant_id | UUID | 租户 ID |
| process_id | UUID | 可以使用的流程 ID |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

约束和边界：

- `tenant_id + process_id` 唯一。
- `tenant_id` 可以引用 `tenant.tenant.id`。
- `process_id` 不建立跨 Schema 外键，由绑定服务写入前校验流程存在。
- 绑定不保存表单、节点、审批人或流程覆盖配置。
- 多个租户绑定同一个流程时，执行完全相同的流程内容。

## 8. 节点类型

### 8.1 START

START 表示流程入口：

- 每条流程必须且只能有一个 START 节点。
- START 不能成为任何连接的目标节点。
- START 不执行业务操作。
- START 完成后由流程编排层选择后续节点。

### 8.2 APPROVAL

APPROVAL 表示人工审批：

- `config_json` 必须配置 `approval_mode`。
- `config_json` 必须至少配置一名有效审批人。
- 进入节点时同时为全部审批人创建待办任务。
- 节点通过后由流程编排层选择后续节点。
- 任意一人拒绝后审批实例直接进入 REJECTED，不再执行后续连接。

### 8.3 END

END 表示审批流程结束：

- 至少有一个 END 节点。
- END 不能作为连接的来源节点。
- `config_json.result_status` 第一版支持 APPROVED、REJECTED。
- 进入 APPROVED 结束节点后，审批运行模块创建后续业务动作任务。

## 9. 多人审批规则

第一版所有审批人任务同时创建，只支持两种审批模式。

### 9.1 AND

- 所有人同意后节点通过。
- 任意一人拒绝后节点立即拒绝。
- 节点拒绝后，其他未处理任务自动取消。

### 9.2 OR

- 任意一人同意后节点立即通过。
- 任意一人拒绝后节点立即拒绝。
- 第一个成功提交的有效结果决定节点最终结果。
- 节点形成结果后，其他未处理任务自动取消。

OR 模式必须通过数据库事务和行锁保证并发操作只能形成一个最终结果。

## 10. 流程编排和分支

节点关系和分支条件统一保存在 `approval_process.orchestration_json`。分支是流程选择下一节点的规则，不是一种节点能力。

```json
{
  "connections": [
    {
      "source_node_id": "开始节点UUID",
      "target_node_id": "财务审批节点UUID"
    },
    {
      "source_node_id": "财务审批节点UUID",
      "target_node_id": "负责人审批节点UUID",
      "condition": {
        "field": "approval_form.amount",
        "operator": "GT",
        "value": 10000
      }
    },
    {
      "source_node_id": "财务审批节点UUID",
      "target_node_id": "审批结束节点UUID",
      "default": true
    },
    {
      "source_node_id": "负责人审批节点UUID",
      "target_node_id": "审批结束节点UUID"
    }
  ]
}
```

含义：

```text
开始
  ↓
财务审批
  ├── amount > 10000 → 负责人审批 → 审批结束
  └── 默认           → 审批结束
```

同一个来源节点只有一条无条件连接时，直接进入目标节点。同一个来源节点存在多条连接时，按照 `connections` 数组中的出现顺序判断条件，第一条命中的连接生效；全部条件未命中时走 `default` 连接。

同一来源节点最多配置一条默认连接。存在多条来源相同的连接时，除了默认连接外，其他连接都必须包含条件。

第一版条件表达式只支持结构化 JSON，不允许执行 Python、JavaScript 或 SQL。首批操作符包括：

```text
EQ、NE、GT、GTE、LT、LTE、IN、NOT_IN、IS_EMPTY、NOT_EMPTY
```

## 11. 流程保存

前端点击保存时提交流程主体、完整节点列表和完整 `orchestration`：

```json
{
  "name": "付款审批流程",
  "form_schema": {},
  "form_ui_schema": {},
  "nodes": [
    {
      "id": "财务审批节点UUID",
      "node_definition_id": "人工审批定义UUID",
      "name": "财务审批",
      "config": {
        "approval_mode": "AND",
        "approvers": [
          {"person_id": "人员UUID"}
        ]
      },
      "position": {"x": 460, "y": 180}
    }
  ],
  "orchestration": {
    "connections": []
  }
}
```

后端在一个数据库事务中完成：

1. 校验流程、表单和节点请求格式。
2. 校验节点定义存在、已启用且 `node_type` 受后端支持。
3. 校验节点 `config` 符合节点定义的配置 Schema。
4. 校验审批人员存在、已启用且没有重复。
5. 新增或更新节点实例，删除本次已移除的节点。
6. 校验并保存流程主体的 `orchestration_json`。
7. 执行完整流程校验并更新流程时间。

任意一步失败时整体回滚。

## 12. 流程完整性校验

保存流程和启用流程时至少校验：

- 节点 ID 在流程内唯一。
- 节点引用的节点定义存在且已启用。
- 节点配置符合对应 `config_schema_json`。
- 恰好一个 START 节点。
- 至少一个 END 节点。
- START 不作为任何连接的目标。
- END 不作为任何连接的来源。
- 每条连接的来源和目标节点都存在且属于当前流程。
- 所有节点都能从 START 到达。
- 所有非 END 节点至少存在一条后续连接。
- 不允许没有出口的死节点。
- 第一版不允许形成环。
- APPROVAL 节点使用 AND 或 OR，并至少配置一名有效审批人。
- 同一来源存在多条连接时，条件格式合法且最多有一条默认连接。
- 条件字段存在于表单 Schema，操作符与字段类型兼容。
- END 节点配置合法的结果状态。

只有完整性校验通过的流程才能设置为 ENABLED。

## 13. 流程状态、复制和快照

流程状态：

| 状态 | 含义 |
|---|---|
| DRAFT | 草稿，不允许发起 |
| ENABLED | 完整且启用，可以被已授权租户使用 |
| DISABLED | 停用，不允许创建新实例 |

复制流程时：

1. 创建新的流程 UUID。
2. 复制表单 Schema、UI Schema 和其他流程资料。
3. 为全部节点生成新的节点 UUID。
4. 复制节点 `config_json` 和 `position_json`。
5. 复制 `orchestration_json`，并把来源和目标 UUID 映射为新节点 UUID。
6. 新流程默认保存为 DRAFT。

发起审批时，审批运行模块必须把以下内容保存到实例快照：

- 流程名称和表单 Schema。
- 全部节点实例及其节点类型。
- 全部节点配置和审批人资料。
- 完整 `orchestration_json`。

审批实例创建后只读取自己的运行快照。修改、停用流程或停用节点定义都不影响已经运行的实例。

## 14. 管理接口

节点定义：

```text
POST  /api/admin/node-definitions
GET   /api/admin/node-definitions
GET   /api/admin/node-definitions/{node_definition_id}
PATCH /api/admin/node-definitions/{node_definition_id}
```

流程管理：

```text
POST  /api/admin/processes
GET   /api/admin/processes
GET   /api/admin/processes/{process_id}
PATCH /api/admin/processes/{process_id}
POST  /api/admin/processes/{process_id}/copy
POST  /api/admin/processes/{process_id}/enable
POST  /api/admin/processes/{process_id}/disable
GET   /api/admin/processes/{process_id}/graph
PUT   /api/admin/processes/{process_id}/graph
POST  /api/admin/processes/{process_id}/validate
```

租户流程授权：

```text
PUT   /api/admin/tenants/{tenant_id}/processes/{process_id}
GET   /api/admin/tenants/{tenant_id}/processes
GET   /api/admin/tenants/{tenant_id}/processes/{process_id}
PATCH /api/admin/tenants/{tenant_id}/processes/{process_id}
```

## 15. 管理页面效果

流程列表展示流程名称、状态、节点数量、已授权租户数量和更新时间，并提供编辑、复制、启停和租户授权入口。

流程设计器：

- 左侧从 `node_definition` 加载节点能力。
- 中间画布创建节点、调整位置并连接节点。
- 右侧编辑节点名称、审批模式和审批人。
- 连接配置面板编辑流程级条件和默认路径。
- 保存时一次提交完整流程、节点和编排关系。

租户授权页面只选择允许使用的流程并设置绑定状态，不配置审批人。

## 16. 本次审批流模块开发范围

本次开发分为四个实现单元：

1. 节点能力管理：`node_definition` 模型、校验、Service、Repository 和管理 API。
2. 流程定义管理：`approval_process` 的基本资料、表单 JSON、状态、复制和管理 API。
3. 节点与编排管理：`approval_process_node`、完整流程保存、读取、关系校验和条件校验。
4. 租户流程授权：`tenant.process_binding`、租户授权接口，以及发起审批前可复用的访问校验能力。

需要同步完成：

- 将四张表及表、字段注释加入 `data/init.sql`。
- 注册第一批 START、APPROVAL、END 节点定义。
- 为关键保存、复制、校验和租户隔离逻辑编写测试。
- 更新整体设计文档和模块 README。

本阶段不创建审批实例、不生成待办任务、不处理审批操作，也不执行业务回调。这些能力分别属于后续审批运行模块和回调执行模块。

## 17. 第一版边界

第一版不实现：

- 显式流程版本管理。
- 顺序审批。
- 租户维度节点配置覆盖。
- 任意脚本条件。
- 流程环路和退回重审。
- 图级并行分支和汇聚节点。
- 动态部门主管、角色、岗位或表达式选人。
- 加签、转交和委托。
- 子流程和定时器节点。
- 业务动作节点。
- 流程导入导出。

节点内部多人审批仍然并行执行；这里排除的是同时执行两条不同流程路径的图级并行。

## 18. 完成标准

1. 可以创建、修改、复制、启停流程。
2. 可以通过前端提交完整节点配置和流程编排。
3. 同一个节点定义可以在一条流程中重复使用并配置不同审批人。
4. 可以配置 AND、OR 多人审批。
5. 可以配置流程级条件分支和默认路径。
6. 可以维护审批表单 Schema 和 UI Schema。
7. 可以校验流程结构并返回明确错误。
8. 可以把同一流程授权给多个租户，租户不覆盖流程配置。
9. 只有流程和租户绑定均为 ENABLED 时才允许发起。
10. 修改流程不会影响已经创建的审批实例。
11. 数据库结构、注释、接口和测试保持一致。
