# 审批流运行模块设计

## 1. 文档目标

本文档定义审批流版本、审批实例、节点执行、审批任务和审批记录的第一版方案。

审批流定义和审批运行统一属于 `process` 模块。代码内部拆分为定义层、运行层和执行引擎，不再建立独立的 `approval` Server 或 `approval` Schema。

## 2. 已确认的核心原则

1. 审批流使用显式版本，不再为每个审批实例重复保存完整流程快照。
2. 业务系统发起审批时只传 `process_id`，系统自动使用当前已发布版本。
3. 草稿版本允许修改；已发布版本永久只读。
4. 流程更新生成新版本，运行中的实例继续绑定原版本。
5. 版本主体和版本节点分表保存，便于数据库约束、节点查询和后续维护。
6. 审批流只支持一条实际运行路径；第一版的并行仅指同一个审批节点同时生成多个人员任务。
7. 多人审批支持 `AND` 和 `OR`，任意一人拒绝都立即拒绝整个审批实例。
8. 审批实例、节点执行、审批任务和审批操作必须完整留痕。
9. 租户关联保存在 `tenant` Schema，`process` 运行表不保存 `tenant_id`。
10. 审批通过后只创建业务执行任务，不在审批数据库事务中直接调用外部 HTTP 接口。

## 3. 模块内部结构

```text
app/server/process/
├── api/
│   ├── node_definition_api.py
│   ├── process_api.py
│   ├── process_version_api.py
│   ├── approval_instance_api.py
│   └── approval_task_api.py
└── src/
    ├── definition/               # 流程、版本和版本节点维护
    ├── runtime/                  # 实例、节点执行、任务和审批记录
    └── engine/                   # 节点执行、条件选择和流程推进
```

现有代码可以逐步迁移到上述目录。本次设计确认后，先完成版本层改造，再开发运行层。

## 4. 流程版本设计

### 4.1 `process.approval_process`

审批流主体只表达一条流程的稳定身份和当前状态。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 稳定的 `process_id` |
| name | VARCHAR(128) | 当前展示名称 |
| description | VARCHAR(500) | 当前说明 |
| status | VARCHAR(20) | `DRAFT`、`ENABLED`、`DISABLED` |
| current_version_id | UUID，可空 | 当前已发布版本 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 最后更新时间 |

业务系统始终传递该表的 `id`，不需要知道版本号。

### 4.2 `process.approval_process_version`

保存每一个流程版本的主体、表单和编排关系。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 版本主键 |
| process_id | UUID | 所属审批流 |
| version_no | INTEGER | 从 1 开始递增的版本号 |
| status | VARCHAR(20) | `DRAFT` 或 `PUBLISHED` |
| name | VARCHAR(128) | 该版本的流程名称 |
| description | VARCHAR(500) | 该版本的流程说明 |
| form_schema_json | JSONB | 该版本的审批表单规则 |
| form_ui_schema_json | JSONB | 该版本的表单展示规则 |
| orchestration_json | JSONB | 该版本的节点连线和条件 |
| revision | INTEGER | 草稿并发保存修订号 |
| created_at | TIMESTAMPTZ | 版本创建时间 |
| updated_at | TIMESTAMPTZ | 草稿最后更新时间 |
| published_at | TIMESTAMPTZ，可空 | 发布时间 |

约束：

- `(process_id, version_no)` 唯一。
- 同一审批流同时最多存在一个 `DRAFT` 版本。
- `PUBLISHED` 版本禁止更新和删除。
- `revision` 每次保存草稿时加一，前端使用它避免整图保存互相覆盖。

### 4.3 `process.approval_process_version_node`

保存某个版本画布中的具体节点。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 当前版本内的节点实例 ID |
| process_version_id | UUID | 所属流程版本 |
| node_definition_id | UUID | 来源节点能力定义 |
| node_type | VARCHAR(32) | 发布时固化的执行类型 |
| name | VARCHAR(128) | 该版本中的节点名称 |
| config_json | JSONB | 审批模式、审批人等配置 |
| position_json | JSONB | 前端画布坐标 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 最后更新时间 |

`node_type` 必须固化在版本节点中。运行时读取版本节点的 `node_type`，不读取后来变化的 `node_definition`。

版本节点 ID 在复制版本时重新生成，`orchestration_json` 中的连线端点同时重映射到新节点 ID。

版本主体和版本节点采用独立表。这样可以对版本节点建立外键和索引，按版本或节点直接
查询，也便于后续关联节点执行记录和统计。整图保存会多一次表写入，但保存动作本来就
需要事务，因此这部分复杂度集中在定义层 Service，不会传递给业务调用方。

## 5. 版本生命周期

### 5.1 新建流程

1. 创建 `approval_process`。
2. 创建 V1 草稿。
3. `approval_process.current_version_id` 暂时为空。
4. 前端编辑 V1 草稿。

### 5.2 首次发布

1. 锁定审批流和 V1 草稿。
2. 执行完整流程校验。
3. 将 V1 设置为 `PUBLISHED`。
4. 将 `current_version_id` 设置为 V1。
5. 将审批流状态设置为 `ENABLED`。

上述操作必须在同一个数据库事务中完成。

### 5.3 编辑已发布流程

1. 复制当前发布版本，生成下一个版本草稿。
2. 复制全部版本节点并生成新的节点 ID。
3. 重写草稿编排中的连线端点。
4. 前端只编辑新草稿，当前发布版本继续提供业务使用。
5. 新版本发布时原子切换 `current_version_id`。

例如 V2 正在编辑时，新发起的实例仍然使用 V1；只有 V2 发布成功后，新实例才使用 V2。

### 5.4 停用流程

停用只改变 `approval_process.status`，阻止创建新实例，不影响已经创建的实例，也不删除历史版本。

## 6. 审批运行表

第一版运行层使用四张表。

### 6.1 `process.approval_instance`

表示一次完整审批申请，同时持久化审批单数据和业务执行参数。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 审批实例 ID |
| process_id | UUID | 审批流 ID |
| process_version_id | UUID | 本次运行使用的已发布版本 |
| business_key | VARCHAR(200) | 业务系统中的原单据标识 |
| idempotency_key | VARCHAR(200) | 内部幂等键，全局唯一 |
| title | VARCHAR(200) | 审批单标题 |
| applicant_person_id | UUID，可空 | 发起人员 ID，不建立跨 Schema 外键 |
| applicant_snapshot_json | JSONB | 发起时的人员展示信息 |
| approval_form_json | JSONB | 给审批人查看的业务数据 |
| execution_payload_json | JSONB | 审批通过后调用业务系统使用的参数 |
| action_code | VARCHAR(100)，可空 | 后续业务动作标识 |
| status | VARCHAR(20) | `RUNNING`、`APPROVED`、`REJECTED`、`CANCELLED`、`ERROR` |
| current_node_execution_id | UUID，可空 | 当前活动节点执行记录 |
| started_at | TIMESTAMPTZ | 发起时间 |
| finished_at | TIMESTAMPTZ，可空 | 结束时间 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 最后更新时间 |

`approval_form_json` 和 `execution_payload_json` 必须分开保存。前者用于审批展示与审计，后者只供审批通过后的业务动作使用。

运行总耗时：

- 运行中：当前时间减 `started_at`。
- 已结束：`finished_at` 减 `started_at`。

第一版不重复保存 `duration_ms`，避免时间字段与耗时字段不一致。查询接口负责计算并返回。

### 6.2 `process.approval_node_execution`

记录实例实际进入过的节点、当前运行位置、实际路径和节点耗时。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 节点执行记录 ID |
| instance_id | UUID | 所属审批实例 |
| process_version_id | UUID | 对应流程版本 |
| node_id | UUID | 版本节点 ID |
| node_type | VARCHAR(32) | 节点执行类型 |
| node_name | VARCHAR(128) | 节点名称快照 |
| sequence_no | INTEGER | 实际执行顺序，从 1 开始 |
| status | VARCHAR(20) | `ACTIVE`、`COMPLETED`、`REJECTED`、`CANCELLED`、`ERROR` |
| entered_at | TIMESTAMPTZ | 进入节点时间 |
| completed_at | TIMESTAMPTZ，可空 | 离开节点时间 |
| next_node_id | UUID，可空 | 实际选择的后续节点 |
| result_json | JSONB | 节点结果、条件命中信息等扩展数据 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 最后更新时间 |

约束：

- `(instance_id, sequence_no)` 唯一。
- 同一个实例同时最多存在一条 `ACTIVE` 节点执行记录。
- 节点完成后不再修改其核心结果。

节点耗时通过 `completed_at - entered_at` 计算；活动节点通过当前时间减 `entered_at` 计算。

该表直接支持后台展示：当前走到哪个节点、每个节点停留多久、实际选择了哪条分支。

### 6.3 `process.approval_task`

进入人工审批节点时，为全部审批人同时创建任务。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 任务 ID |
| instance_id | UUID | 所属审批实例 |
| node_execution_id | UUID | 所属节点执行记录 |
| approver_person_id | UUID | 审批人 ID，不建立跨 Schema 外键 |
| approver_snapshot_json | JSONB | 审批人当时的姓名等展示信息 |
| status | VARCHAR(20) | `PENDING`、`APPROVED`、`REJECTED`、`CANCELLED` |
| created_at | TIMESTAMPTZ | 待办产生时间 |
| handled_at | TIMESTAMPTZ，可空 | 审批完成时间 |
| cancelled_at | TIMESTAMPTZ，可空 | 被系统取消时间 |
| updated_at | TIMESTAMPTZ | 最后更新时间 |

约束 `(node_execution_id, approver_person_id)` 唯一，防止给同一审批人重复创建任务。

### 6.4 `process.approval_record`

保存审批人的实际操作，是不可修改的审计记录。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID | 记录 ID |
| instance_id | UUID | 所属审批实例 |
| node_execution_id | UUID | 所属节点执行记录 |
| task_id | UUID | 对应审批任务 |
| operator_person_id | UUID | 实际操作人员 ID |
| operator_snapshot_json | JSONB | 操作人员展示信息 |
| action | VARCHAR(20) | `APPROVE` 或 `REJECT` |
| comment | TEXT，可空 | 审批意见 |
| created_at | TIMESTAMPTZ | 操作时间 |

第一版一个任务只能产生一条最终审批记录，因此 `task_id` 唯一。

## 7. 租户关联与使用记录

租户模块后续增加两张表：

### 7.1 `tenant.process_binding`

控制一个租户是否可以发起指定审批流，只保存租户、审批流和启停状态。

### 7.2 `tenant.process_usage_record`

记录租户实际使用审批流的事实，同时为租户查询审批实例提供作用域入口。

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 使用记录 ID |
| tenant_id | 租户 ID |
| process_id | 审批流 ID |
| process_version_id | 实际使用版本 ID |
| approval_instance_id | 审批实例 ID |
| business_key | 租户业务单据标识 |
| created_at | 创建时间 |

租户表不重复保存审批状态、当前节点或耗时。详细运行信息统一从 `process` 运行表读取，避免两份状态不一致。

第一版建议对 `(tenant_id, process_id, business_key)` 建立唯一约束，用于阻止同一租户对同一业务单据重复发起审批。

关闭租户能力时，不创建租户使用记录，审批运行模块仍然可以独立工作。

## 8. 发起审批流程

请求示例：

```json
{
  "business_key": "PAY-20260921-001",
  "title": "供应商付款申请",
  "applicant_person_id": "人员UUID",
  "action_code": "PAYMENT_EXECUTE",
  "approval_form": {
    "amount": 10000,
    "reason": "采购付款"
  },
  "execution_payload": {
    "payment_id": "PAY-20260921-001",
    "amount": 10000
  }
}
```

处理顺序：

1. 解析可选租户作用域。
2. 租户模式下校验 `tenant.process_binding`。
3. 查询审批流并确认状态为 `ENABLED`。
4. 锁定审批流，读取 `current_version_id` 对应的已发布版本和全部版本节点。
5. 按版本表单 Schema 校验 `approval_form`。
6. 校验申请人和业务参数。
7. 根据租户、流程和 `business_key` 生成内部幂等键。
8. 创建审批实例并绑定确定的 `process_version_id`。
9. 租户模式下创建 `tenant.process_usage_record`。
10. 执行 START 节点并自动推进，直到进入 APPROVAL 或 END 节点。
11. 进入 APPROVAL 时，同时创建全部审批任务。
12. 在一个事务中提交实例、节点执行和首批任务。

相同幂等键重复请求时返回原审批实例，不重复创建流程。

幂等键只表达“同一个业务单据”，不能说明请求内容是否相同，因此实例同时保存发起请求
的内容摘要。重放时比对摘要：内容一致返回原实例，内容已经变化（审批单数据、业务执行
参数、业务动作、标题或发起人不同）返回 409，避免新的审批数据被静默忽略后继续使用
旧的执行参数。

## 9. 流程推进规则

### 9.1 START 节点

START 不产生人工任务。进入后立即完成，根据编排选择后续节点。

### 9.2 APPROVAL 节点

进入节点时：

1. 创建一条 `approval_node_execution`，状态为 `ACTIVE`。
2. 读取版本节点配置中的审批模式和审批人。
3. 为所有审批人同时创建 `PENDING` 任务。
4. 将实例的 `current_node_execution_id` 指向该记录。

AND 模式：

- 所有任务都同意后节点通过。
- 任意一人拒绝后实例立即拒绝。
- 拒绝后其余待处理任务全部取消。

OR 模式：

- 任意一人同意后节点通过。
- 任意一人拒绝后实例立即拒绝。
- 第一个成功提交的结果形成节点最终结果，其余待处理任务全部取消。

### 9.3 条件与默认路径

节点通过后，按 `orchestration_json.connections` 中的顺序判断条件：

1. 依次判断当前节点的条件连线。
2. 选择第一条命中的条件连线。
3. 没有条件命中时选择唯一默认路径。

条件字段的取值类型决定比较方式：数字按数值比较，`date`、`date-time`、`time` 字段按
表单 Schema 声明的 format 解析后比较，`date-time` 统一换算到 UTC。带时区或写法不同
的合法时间字符串字典序与真实时间顺序可能相反，不能直接比较字符串。取值缺失或无法
按声明格式解析时按不命中处理，由默认路径兜住。

定义模块已经要求存在条件连线时必须提供默认路径，因此运行时不会因为全部条件未命中而停住。

### 9.4 END 节点

- `result_status=APPROVED`：实例更新为 `APPROVED`，记录结束时间，并创建业务执行任务。
- `result_status=REJECTED`：实例更新为 `REJECTED`，记录结束时间。

业务执行任务属于 `callback` 模块。审批事务只写入任务，不直接请求业务系统。

## 10. 审批操作与并发控制

审批操作必须在单个事务中完成：

1. 使用 `SELECT ... FOR UPDATE` 锁定审批实例。
2. 查询并锁定当前任务。
3. 校验实例、节点和任务仍处于可处理状态。
4. 写入不可变审批记录。
5. 更新当前任务状态。
6. 按 AND 或 OR 计算节点结果。
7. 取消不再需要的待处理任务。
8. 完成节点执行记录并推进下一节点，或者结束实例。
9. 提交事务。

锁定审批实例可以把同一节点上的并发审批操作串行化，保证 OR 模式只形成一个最终结果，也保证拒绝与同意不会同时推进流程。

重复提交相同操作时：

- 任务已经以相同结果完成，返回当前结果，不重复写记录。
- 任务已经被其他结果处理或取消，返回 409。

## 11. 实时运行视图

后台详情页可以展示：

- 租户、业务单号和审批标题。
- 使用的流程名称和版本号。
- 实例当前状态和当前节点。
- 总运行时长。
- 每个实际经过节点的进入时间、完成时间和处理时长。
- 当前待办人员。
- 已审批人员、意见和处理时长。
- 条件分支实际选择的下一节点。
- 审批结束后的业务执行状态。

第一版直接从实例、节点执行、任务和审批记录查询。数据量增大后，可以增加统计汇总表或物化视图，但不在租户使用记录中重复保存运行状态。

## 12. 第一版接口

```text
POST /api/processes/{process_id}/instances                   发起审批
GET  /api/approval-instances/{instance_id}                  查询审批详情
GET  /api/approval-instances/{instance_id}/timeline         查询运行时间线
GET  /api/approval-tasks?person_id=...&status=PENDING       查询人员待办或已办
POST /api/approval-tasks/{task_id}/approve                  同意任务
POST /api/approval-tasks/{task_id}/reject                   拒绝任务
```

正式接入项目平台前，任务查询和审批请求显式传递 `person_id`。接入可信登录身份后，由 FastAPI 依赖注入当前人员身份，接口不再接受调用方任意指定操作人。

## 13. 当前不做的能力

- 顺序会签。
- 图级并行分支和汇聚。
- 撤回、退回、转交、加签和委托。
- 动态审批人表达式。
- 子流程、定时器和脚本节点。
- 管理端手动修改运行中的实例。
- 用户手动选择历史流程版本发起审批。
- 独立的统计汇总表。

## 14. 开发顺序

1. 将现有无版本流程定义改造成流程、版本、版本节点结构。
2. 完成草稿复制、修订号校验、发布和当前版本切换。
3. 建立四张审批运行表。
4. 实现发起审批、版本绑定和幂等处理。
5. 实现节点执行引擎和条件路径选择。
6. 实现 AND、OR 任务决策与并发锁。
7. 实现审批详情、待办和时间线接口。
