# 租户作用域设计

> 设计状态：已确认，后续业务模块必须遵守。  
> 实现状态：基础能力、人员绑定和业务接入模块的流程、业务动作、审批实例三类绑定均已落地；一期部门不与租户绑定。

## 1. 目标

租户能力是审批中心的可选扩展。业务模块的表结构和核心服务不依赖租户，关闭租户能力后系统仍能以全局模式正常运行。

租户模块负责：

- API Key 认证并解析当前租户。
- 保存租户与业务聚合根的归属关系。
- 为业务模块提供统一的资源过滤、访问校验和绑定能力。
- 保存租户特有的扩展配置。

业务模块负责：

- 自身业务表和业务规则。
- 在 API 或 Service 中按需调用 TenantScope。
- 不在业务表中保存 tenant_id。
- 不建立指向 tenant Schema 的外键。

代码允许调用租户作用域能力，数据库表结构不反向依赖租户。

## 2. 两种运行模式

使用配置：

```text
TENANCY_ENABLED=true
```

### 2.1 租户模式

当 `TENANCY_ENABLED=true` 时：

- 业务请求必须提供有效的 `X-API-Key`。
- TenantScope 解析可信 tenant_id。
- 列表查询只返回当前租户已绑定的资源。
- 详情、修改和删除前必须验证资源归属。
- 创建业务聚合根后，在同一事务中建立租户绑定。

缺少或无效 API Key 必须返回 401，不能自动降级为全局模式。

### 2.2 全局模式

当 `TENANCY_ENABLED=false` 时：

- 不要求 `X-API-Key`。
- 业务查询不追加租户过滤。
- 资源访问校验直接通过。
- 建立和解除租户绑定是空操作。
- tenant Schema 可以不存在。

## 3. 统一代码接口，拆分物理关联表

业务模块统一调用 TenantScope，但数据库不使用一张不断增长的通用资源表。

关联表按照业务聚合拆分，并统一放在 tenant Schema：

```text
tenant.person_binding
tenant.process_binding
tenant.business_action_binding
tenant.process_usage_record
```

只给聚合根建立租户绑定。审批任务、审批记录、回调尝试等子数据通过聚合根推导归属，不单独建立绑定表。

## 4. 为什么不使用统一 resource_binding

单一 `tenant.resource_binding` 会把人员、流程和高频审批实例混在一起，长期会产生：

- 索引持续膨胀。
- 所有模块竞争同一张热点表。
- 不同资源的唯一约束难以表达。
- attributes JSONB 逐渐承载无约束业务数据。
- 审批历史归档影响人员和流程配置关系。

拆表后仍然保留统一调用体验，同时可以分别建立索引、唯一约束、归档和分区策略。

## 5. 关联表设计

### 5.1 tenant.person_binding

保存租户可见人员及租户内人员资料。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| tenant_id | UUID | 租户 ID |
| person_id | UUID | organization.person ID |
| employee_no | VARCHAR(64) | 可选租户内工号 |
| external_user_id | VARCHAR(128) | 可选项目平台用户标识 |
| display_name | VARCHAR(100) | 可选租户内展示名称 |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

约束：

- tenant_id + person_id 唯一。
- tenant_id + employee_no 在非空时唯一。
- tenant_id + external_user_id 在非空时唯一。

### 5.2 tenant.process_binding

保存租户可以使用的公共审批流。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| tenant_id | UUID | 租户 ID |
| process_id | UUID | process.approval_process ID |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

该表只控制租户能否使用流程，不保存或覆盖流程节点和审批人配置。

### 5.3 tenant.business_action_binding

保存租户可以使用的业务动作。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| tenant_id | UUID | 租户 ID |
| business_action_id | UUID | integration.business_action ID |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

约束 tenant_id + business_action_id 唯一。

第一版绑定只表达使用权限。动作的接口配置统一保存在 `integration.business_action`，
租户之间通过各自的 `callback_base_url` 区分，绑定表不再保存路径覆盖、凭据引用和超时
配置，这些能力在确有需要时再加入。

### 5.4 tenant.process_usage_record

保存审批实例归属和发起幂等信息。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| tenant_id | UUID | 租户 ID |
| approval_instance_id | UUID | process.approval_instance ID |
| process_id | UUID | 发起时流程 ID |
| process_version_id | UUID | 发起时实际使用的流程版本 ID |
| business_key | VARCHAR(200) | 原业务单据标识 |
| action_code | VARCHAR(100) | 可选业务动作标识 |
| created_at | TIMESTAMPTZ | 创建时间 |

约束：

- approval_instance_id 唯一。
- tenant_id + process_id + business_key 唯一。

使用记录是历史事实，写入后不修改也不删除，因此没有 `updated_at`。审批状态、当前节点
和耗时统一从 process 运行表读取后组装，不在使用记录中重复保存。

## 6. 数据库解耦规则

为保证删除 tenant Schema 后业务模块仍能运行：

- organization、process 和 integration 的业务表不含 tenant_id。
- 业务表不引用 tenant Schema。
- tenant 关联表可以保存业务资源 UUID，但不建立跨 Schema 外键。
- tenant 模块在绑定前通过业务 Service 校验资源存在。
- 同一数据库内创建资源和绑定时必须共用事务。
- 增加后台对账任务，检查失效或孤立绑定。

tenant 关联表仍然可以对 `tenant_id` 建立指向 `tenant.tenant.id` 的外键。

## 7. TenantScope 接口

TenantScope 是业务模块调用租户能力的统一入口。

```python
class TenantScope:
    """统一提供租户资源过滤、校验和绑定能力。"""

    def apply_filter(self, statement, resource_id_column):
        """为查询追加当前租户的资源过滤条件。"""

    def require_access(self, resource_id, db):
        """确认当前租户拥有指定资源。"""

    def bind(self, resource_id, db, attributes=None):
        """建立当前租户与业务资源的绑定。"""

    def unbind(self, resource_id, db):
        """停用当前租户与业务资源的绑定。"""
```

业务代码不直接查询具体 binding 表。

## 8. 资源注册定义

TenantScope 根据 resource_type 选择绑定定义。四类资源都已经实现：

```text
organization.person           → tenant.person_binding（已实现）
process.approval_process      → tenant.process_binding（已实现）
integration.business_action   → tenant.business_action_binding（已实现）
process.approval_instance     → tenant.process_usage_record（已实现）
```

前三种绑定都有 `ENABLED`、`DISABLED` 状态，审批使用记录没有启停状态：记录存在即代表
租户可以访问该审批实例。因此绑定定义额外声明了两个差异点：`status_field` 为空表示
不做状态判断，`required_attribute_fields` 列出写入时必须由调用方提供的资源特有字段。

每项绑定定义负责：

- 使用哪张绑定表。
- 如何追加 EXISTS 过滤。
- 如何验证访问权限。
- 如何建立或停用绑定。
- 如何处理资源特有字段。

## 9. FastAPI 使用方式

使用 Dependency 工厂获得接近装饰器的调用体验：

```python
def use_tenant_scope(resource_type: str):
    """创建指定资源类型的租户作用域依赖。"""
```

列表查询使用 `use_tenant_scope(resource_type)` 获取统一资源作用域。对于通过路径参数访问单个资源的接口，可以使用通用访问守卫。业务接口只声明资源类型和资源 ID 参数名，不需要解析 API Key 或查询租户表：

```python
@router.get(
    "/persons/{person_id}",
    dependencies=[require_tenant_access("organization.person", "person_id")],
)
def get_person(person_id: UUID):
    """查询已经通过租户访问校验的人员。"""

    return person_service.get_person(person_id)
```

访问守卫会解析可信租户上下文、读取路径中的资源 UUID，并通过注册的绑定定义查询对应 binding 表。绑定有效时继续执行，无绑定或绑定已停用时返回 403。`TENANCY_ENABLED=false` 时，全局作用域会直接放行。


列表接口：

```python
@router.get("/admin/persons")
def list_persons(
    scope: TenantScope = use_tenant_scope("organization.person"),
    db: Session = Depends(get_postgres_engine),
):
    """查询当前作用域可见的人员。"""

    return person_service.list_persons(db, scope)
```

详情和修改：

```python
scope.require_access(person_id, db)
```

创建：

```python
person = person_service.create_person(request, db)
scope.bind(person.id, db)
db.commit()
```

API 继续放在业务模块中，tenant 模块不接管业务 API。

## 10. 查询实现

列表过滤使用 SQL EXISTS，不先把资源 ID 全部读取到 Python：

```sql
SELECT person.*
FROM organization.person AS person
WHERE EXISTS (
    SELECT 1
    FROM tenant.person_binding AS binding
    WHERE binding.tenant_id = :tenant_id
      AND binding.person_id = person.id
      AND binding.status = 'ENABLED'
);
```

全局模式下 `apply_filter()` 原样返回业务查询。

## 11. 默认实现

TenantScope 提供两个实现：

### TenantResourceScope

租户模式使用：

- 持有可信 tenant_id。
- 查询对应 binding 表。
- 执行过滤、校验、绑定和解绑。

### GlobalResourceScope

全局模式使用：

- apply_filter 原样返回查询。
- require_access 直接通过。
- bind 和 unbind 是空操作。

业务模块不需要编写 `if TENANCY_ENABLED`。

## 12. 事务规则

创建业务资源时：

```text
创建业务聚合根
    ↓
TenantScope.bind
    ↓
创建必要的业务子数据
    ↓
提交同一数据库事务
```

任何一步失败都整体回滚。

如果未来 tenant 与业务模块拆分到不同数据库，需要改为事件和可靠消息，不继续使用跨库事务。

## 14. 验收标准

- 业务表不存在 tenant_id。
- 业务表不存在指向 tenant Schema 的外键。
- API 仍然位于各业务 server。
- TENANCY_ENABLED=false 时无需 tenant 表即可运行。
- TENANCY_ENABLED=true 时列表、详情、修改和创建都经过 TenantScope。
- 人员、流程和审批实例使用独立绑定表。
- 业务模块不直接查询 binding 表。
- 租户模式和全局模式都有完整测试。
