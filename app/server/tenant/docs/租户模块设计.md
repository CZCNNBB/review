# 租户模块设计

## 1. 模块范围

第一版将一个接入业务系统视为一个租户。租户模块负责：

- 维护租户编码、名称、状态和默认回调基础地址。
- 为租户创建、查询和撤销 API Key。
- 通过 API Key 建立可信租户上下文。
- 为审批中心回调业务系统维护加密保存的 Service Token 凭据。
- 作为可选能力维护租户与各业务聚合根的绑定关系。
- 向其他模块提供统一 TenantScope 过滤、校验和绑定接口。

租户与人员、审批流、业务动作和审批实例的关系由 tenant Schema 中的独立 binding 表维护。第一版部门保持全局平铺，不与租户绑定。业务模块的表结构不保存 tenant_id。

## 2. 数据表

租户服务使用独立的 PostgreSQL Schema `tenant`。本模块中的物理表全名为：

```text
tenant.tenant
tenant.tenant_api_key
tenant.tenant_callback_credential
```

后续其他 `server` 模块使用自己的 Schema，避免所有模块的数据表堆放在 `public` 中。

所有模块的首次建库结构统一维护在 `backend/data/init.sql`，不再为每个 server 分散保存初始化 SQL。

### tenant.tenant

保存租户基本资料。租户采用状态停用，不提供物理删除接口。

| 字段 | 说明 |
|---|---|
| id | UUID 主键 |
| code | 全局唯一租户编码，统一大写 |
| name | 租户名称 |
| description | 可选说明 |
| callback_base_url | 默认回调基础地址，保存时移除末尾斜杠 |
| status | ENABLED、DISABLED |
| created_at / updated_at | UTC 时间 |

### tenant.tenant_api_key

API Key 用于业务系统调用审批中心。第一版按照当前项目约定直接保存完整明文，管理页面可以查询和复制。

| 字段 | 说明 |
|---|---|
| id | UUID 主键 |
| tenant_id | 所属租户 |
| name | 凭据用途名称 |
| api_key | 全局唯一的完整 API Key 明文 |
| status | ACTIVE、DISABLED、EXPIRED、REVOKED |
| expires_at | 可选过期时间 |
| last_used_at | 最近验证成功时间 |
| created_at / revoked_at | 创建和撤销时间 |

明文格式：

```text
appr_live_{key_prefix}.{random_secret}
```

### tenant.tenant_callback_credential

第一版回调认证方案为 Service Token。业务系统为审批中心服务账号签发长期 Token，审批中心
复用业务系统已有认证请求头。Token 发送回业务系统时必须能够还原，因此使用
`APPROVAL_CREDENTIAL_MASTER_KEY` 加密保存，不能只保存哈希。模型、Schema、Service 和管理
接口都已按下面的结构实现。

早期 HMAC 结构的 `key_id` 和 `secret_ciphertext` 列不再使用。已有开发库执行
`data/migrations/20260922_callback_credential_service_token.sql` 完成升级，脚本发现 `ACTIVE`
凭据时会主动中止；全新库由 `data/init.sql` 直接创建 Service Token 结构。

| 字段 | 说明 |
|---|---|
| id | UUID 主键 |
| tenant_id | 所属租户 |
| name | 凭据用途名称 |
| header_name | 业务系统已有的认证请求头名称，默认 Authorization |
| token_prefix | Token 前缀，默认 Bearer，允许为空 |
| token_ciphertext | Fernet 加密后的 Service Token |
| status | ACTIVE、REVOKED |
| expires_at | 可选过期时间 |
| created_at / revoked_at | 创建和撤销时间 |

创建接口由管理员提交明文 Token，服务收到后立即加密，响应只返回元数据，不返回明文或
密文。创建新凭据时在同一事务中自动撤销旧的 `ACTIVE` 凭据并写入新凭据；数据库建立
`WHERE status = 'ACTIVE'` 的部分唯一索引，确保一个租户同时最多存在一条有效凭据。

当业务执行 Worker 启用时，`APPROVAL_CREDENTIAL_MASTER_KEY` 缺失或格式错误应直接阻止
应用启动，不能等到执行任务时再让全部任务失败。

## 3. 接口

管理接口统一要求 X-Admin-Key：

```text
POST  /api/admin/tenants
GET   /api/admin/tenants
GET   /api/admin/tenants/{tenant_id}
PATCH /api/admin/tenants/{tenant_id}

POST  /api/admin/tenants/{tenant_id}/api-keys
GET   /api/admin/tenants/{tenant_id}/api-keys
POST  /api/admin/tenants/{tenant_id}/api-keys/{api_key_id}/revoke

POST  /api/admin/tenants/{tenant_id}/callback-credentials
GET   /api/admin/tenants/{tenant_id}/callback-credentials
POST  /api/admin/tenants/{tenant_id}/callback-credentials/{credential_id}/revoke
```

业务系统可使用自己的 X-API-Key 验证身份：

```text
GET /api/tenant/context
```

## 4. 环境配置

```text
APPROVAL_ADMIN_KEY=租户管理临时管理密钥
APPROVAL_CREDENTIAL_MASTER_KEY=Fernet应用主密钥
```

APPROVAL_ADMIN_KEY 只作为项目平台管理员身份接入前的临时保护措施。正式接入后，应替换为平台可信用户身份和管理员判断。

## 5. 当前边界

- 不提供租户物理删除。
- API Key 和回调凭据撤销后不可恢复，需要重新创建。
- 业务动作相对路径保存在 `integration.business_action.relative_path`，由业务接入模块维护。
- 执行记录生成、Service Token 解密和 HTTP 发送在 process 业务执行子模块实现。
- 租户资源关联统一在 tenant 模块实现，业务模块只通过 TenantScope 调用。
- 全新环境通过统一 `data/init.sql` 初始化，正式环境结构变更需要引入数据库迁移工具。

## 6. 资源绑定表

```text
tenant.person_binding             租户可见人员及租户内人员资料
tenant.process_binding            租户可以使用的审批流
tenant.business_action_binding    租户可以使用的业务动作
tenant.process_usage_record       审批实例归属和发起幂等信息
```

关联表按业务聚合拆分，避免使用单一的大型 resource_binding 表。四张表都已经实现，
授权记录只提供启用和停用，不物理删除。详细设计见同目录下的 `租户作用域设计.md`，
流程授权、动作授权和使用记录的接口见
`app/server/integration/docs/业务接入接口说明.md`。
