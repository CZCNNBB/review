# 人员与组织模块设计

> 目标设计状态：已确认。  
> 当前实现状态：已完成基础表、服务、管理 API 和租户绑定重构。

## 1. 模块目标

人员与组织模块是独立业务模块，不感知租户是否存在。

该模块负责：

- 全局人员资料。
- 全局平铺部门。
- 人员与部门关系。
- 人员、部门的启用和停用。

该模块不负责：

- 用户名密码登录。
- 租户创建和租户状态。
- 人员属于哪些租户。
- 部门属于哪些租户。
- 租户 API Key。
- 角色权限系统。
- 多级组织树。

租户可见范围由 tenant 模块通过 TenantScope 和绑定表扩展。

## 2. PostgreSQL Schema

业务表位于：

```text
organization.person
organization.department
organization.department_member
```

所有表都不保存 tenant_id，也不建立指向 tenant Schema 的外键。

## 3. 表设计

### 3.1 organization.person

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| name | VARCHAR(100) | 姓名 |
| mobile | VARCHAR(32) | 可选手机号 |
| email | VARCHAR(255) | 可选邮箱 |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

手机号和邮箱只作为人员资料，不作为登录凭据。

### 3.2 organization.department

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| code | VARCHAR(64) | 全局唯一部门编码 |
| name | VARCHAR(100) | 部门名称 |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

第一版不保存 parent_id。

### 3.3 organization.department_member

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| department_id | UUID | 部门 ID |
| person_id | UUID | 人员 ID |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

第一版允许一个人员加入多个部门。department_id + person_id 唯一。

## 4. 租户扩展

租户关系不进入 organization Schema，保存在：

```text
tenant.person_binding
tenant.department_binding
```

人员业务 API 仍然位于 organization server，并通过 TenantScope 按需过滤。

租户模式：

```text
organization.person
    ↑ person_id
tenant.person_binding
    ↑ tenant_id
tenant.tenant
```

全局模式不查询 binding 表。

详细规则见：

```text
backend/docs/租户作用域设计.md
```

## 5. API 设计

### 5.1 人员

```text
POST  /api/admin/persons
GET   /api/admin/persons
GET   /api/admin/persons/{person_id}
PATCH /api/admin/persons/{person_id}
```

### 5.2 部门

```text
POST  /api/admin/departments
GET   /api/admin/departments
GET   /api/admin/departments/{department_id}
PATCH /api/admin/departments/{department_id}
```

### 5.3 部门成员

```text
POST  /api/admin/departments/{department_id}/members
GET   /api/admin/departments/{department_id}/members
POST  /api/admin/departments/{department_id}/members/{person_id}/disable
```

以上接口是平台管理员维护全局人员与组织资料的接口，统一使用管理密钥，不做租户过滤。租户可见人员和部门通过本模块下的租户绑定接口维护：

```text
POST  /api/admin/tenants/{tenant_id}/persons/bind
GET   /api/admin/tenants/{tenant_id}/persons
PATCH /api/admin/tenants/{tenant_id}/persons/{person_id}/binding
POST  /api/admin/tenants/{tenant_id}/departments/bind
GET   /api/admin/tenants/{tenant_id}/departments
```

后续提供给业务系统调用的接口通过 `use_tenant_scope(resource_type)` 自动取得租户或全局作用域。

## 6. TenantScope 使用

列表查询：

```python
statement = tenant_scope.apply_filter(
    statement=select(Person),
    resource_id_column=Person.id,
)
```

详情和修改：

```python
tenant_scope.require_access(person_id, db)
```

创建：

```python
person = person_service.create_person(request, db)
tenant_scope.bind(person.id, db)
db.commit()
```

全局模式下这些调用不会追加过滤或写入绑定表。

## 7. 关键规则

- 停用人员后不能创建新的审批任务。
- 已完成审批记录继续展示人员快照。
- 停用部门不物理删除历史关系。
- organization Service 不导入 TenantRepository。
- organization Repository 不直接查询 tenant Schema。
- 租户过滤只能通过 TenantScope 完成。
- 人员与部门创建和租户绑定必须在同一事务提交。

## 9. 完成标准

- organization 表中没有 tenant_id。
- organization 模块可以在 tenant 模块不存在时独立运行。
- 全局模式可以管理全部人员、部门和部门成员。
- 租户模式只返回当前租户绑定的人员和部门。
- 同一人员和部门可以绑定多个租户。
- API 路径和业务响应不随租户模式变化。
