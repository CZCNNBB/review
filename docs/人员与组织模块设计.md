# 人员与组织模块设计

> 实现状态：第一版后端、数据库结构和管理接口已完成。

## 1. 为什么下一步做这个模块

审批流节点最终必须指定审批人。租户模块完成后，流程模块依赖的最小前置数据是：

- 平台中有哪些人员。
- 某个人属于哪些租户。
- 某个租户有哪些部门。
- 流程节点可以选择哪些租户成员作为审批人。

因此租户模块之后先实现 `organization` server，再开始审批流定义模块。

## 2. 模块边界

人员与组织模块负责：

- 手工创建和维护全局人员。
- 维护租户下的平铺部门。
- 将人员添加为租户成员。
- 保存项目平台的外部用户标识，为后续登录身份映射预留字段。
- 向审批流模块提供可选择的租户成员。

本模块不负责：

- 用户名密码登录。
- 角色和权限系统。
- 多级组织树。
- 岗位、职级和汇报关系。
- 从项目平台自动同步人员。

## 3. PostgreSQL Schema

本模块使用：

```text
organization
```

物理表为：

```text
organization.person
organization.department
organization.tenant_member
```

初始化结构继续追加到统一文件：

```text
backend/data/init.sql
```

## 4. 表设计

### 4.1 organization.person

保存审批中心能够识别的全局人员。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| name | VARCHAR(100) | 姓名 |
| mobile | VARCHAR(32) | 可选手机号 |
| email | VARCHAR(255) | 可选邮箱 |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

手机号和邮箱第一版只作为人员资料，不作为登录凭据。

### 4.2 organization.department

保存租户内部的平铺部门。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| tenant_id | UUID | 外键指向 tenant.tenant |
| code | VARCHAR(64) | 租户内唯一部门编码 |
| name | VARCHAR(100) | 部门名称 |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

第一版不保存 `parent_id`，后续需要组织树时再扩展。

### 4.3 organization.tenant_member

连接全局人员与租户。流程审批人应引用该表的 `id`。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键，也作为 tenant_member_id |
| tenant_id | UUID | 外键指向 tenant.tenant |
| person_id | UUID | 外键指向 organization.person |
| department_id | UUID | 可选，指向当前租户的部门 |
| employee_no | VARCHAR(64) | 可选，租户内人员编号 |
| external_user_id | VARCHAR(128) | 可选，项目平台用户标识 |
| display_name | VARCHAR(100) | 可选租户内展示名称 |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

建议约束：

- `tenant_id + person_id` 唯一。
- 非空时，`tenant_id + employee_no` 唯一。
- 非空时，`tenant_id + external_user_id` 唯一。
- 部门必须属于同一个租户，这一规则由服务层校验。

## 5. 第一版接口

### 5.1 人员

```text
POST  /api/admin/persons
GET   /api/admin/persons
GET   /api/admin/persons/{person_id}
PATCH /api/admin/persons/{person_id}
```

### 5.2 部门

```text
POST  /api/admin/tenants/{tenant_id}/departments
GET   /api/admin/tenants/{tenant_id}/departments
PATCH /api/admin/tenants/{tenant_id}/departments/{department_id}
```

### 5.3 租户成员

```text
POST  /api/admin/tenants/{tenant_id}/members
GET   /api/admin/tenants/{tenant_id}/members
GET   /api/admin/tenants/{tenant_id}/members/{member_id}
PATCH /api/admin/tenants/{tenant_id}/members/{member_id}
```

初期继续使用 `X-Admin-Key` 保护管理接口。

## 6. 关键业务规则

- 停用人员后，该人员不能再被新增为审批人。
- 停用租户成员后，不能再为其创建新的审批任务。
- 已经完成的审批记录必须继续展示原人员快照。
- 删除部门时采用停用，不物理删除。
- 人员退出某租户时停用租户成员关系，不删除全局人员。
- 流程节点保存 `tenant_member_id`，审批实例创建时再保存审批人快照。
- 外部登录身份接入后，通过租户和 `external_user_id` 定位租户成员。

## 7. 本模块完成标准

- 可以手工创建全局人员。
- 可以为租户创建平铺部门。
- 可以把人员添加到一个或多个租户。
- 可以按租户查询可用成员。
- 可以停用人员、部门或租户成员。
- 可以通过 `tenant_id + external_user_id` 找到唯一租户成员。
- 跨租户部门绑定会被拒绝。
- 数据库结构加入统一 `data/init.sql`。
