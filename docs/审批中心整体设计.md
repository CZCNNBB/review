# 审批中心整体设计

## 1. 文档目标

本文档沉淀审批中心当前已经确认的整体设计，作为后端模块拆分、数据库建模、接口实现和前端页面设计的共同依据。

当前阶段优先完成一个可运行、可接入业务系统的审批中心。暂不建设完整权限平台、复杂组织树和流程版本管理。

## 2. 产品定位

审批中心只负责审批领域本身：

- 维护可以被业务系统使用的审批流。
- 接收业务系统提交的审批申请。
- 保存审批单展示数据和业务执行参数。
- 根据流程生成审批任务并记录审批过程。
- 审批通过后调用业务系统配置的业务动作接口。
- 保存回调结果，支持查询、重试和审计。

审批中心不理解付款、采购、合同等具体业务规则，也不直接修改业务系统的数据。

例如付款申请的完整链路为：

```text
付款系统提交申请
    ↓
审批中心按照 process_id 创建审批实例
    ↓
审批人查看付款申请数据并审批
    ↓
全部审批通过
    ↓
审批中心调用付款系统配置的 action_code 对应接口
    ↓
付款系统执行业务并返回结果
    ↓
审批中心记录执行结果
```

## 3. 已确认的核心规则

### 3.1 租户

- 一个租户代表一个接入审批中心的业务系统。
- 每个租户拥有自己的 API Key 和默认回调基础地址。
- 业务系统调用审批中心时通过 `X-API-Key` 确定租户身份。
- 第一版 API Key 直接以明文保存，管理页面可以查看和复制。
- 请求中的 `tenant_id` 不能替代 API Key 身份，只能用于业务核对。

### 3.2 审批流

- 每条审批流具有稳定且唯一的 `process_id`。
- 业务系统发起审批时必须明确传入 `process_id`。
- 租户与审批流是多对多关系，通过关系表控制某租户能否使用某审批流。
- 第一版不提供显式版本号，流程管理页面始终编辑当前最新配置。
- 创建审批实例时必须保存流程、节点、连线和审批人的运行快照。
- 流程修改只影响之后创建的新实例，不影响已经运行的实例。

### 3.3 人员与登录

- 审批中心不提供独立账号密码登录。
- 正式接入后复用上层项目平台的登录身份。
- 第一版人员、租户成员和部门由审批中心管理页面手动维护。
- 人员和部门是全局业务数据，核心表不保存 tenant_id。
- 部门第一版采用平铺结构，不处理上下级部门。
- 开启租户能力时，通过 tenant.person_binding 和 tenant.department_binding 控制租户可见范围。
- 关闭租户能力时，人员和部门模块按全局模式独立运行。

### 3.4 审批数据

一次申请至少保存两类数据：

- `approval_form`：给审批人查看的审批单快照。
- `execution_payload`：审批通过后调用业务接口使用的参数。

两类数据可以来源于同一次业务请求，但用途不同。保存快照可以保证审批期间业务数据变化后，仍能还原当时的申请内容和审批依据。

### 3.5 业务动作与回调

- 每个租户可以维护多个业务动作，使用稳定的 `action_code` 标识。
- 动作配置保存请求方法、相对路径、参数校验规则、超时和成功判定。
- 完整调用地址由租户的 `callback_base_url` 与动作相对路径组成。
- 审批通过后只创建一次业务执行任务，使用幂等键避免重复执行。
- 执行失败需要保存请求、响应、错误和重试次数。
- 回调签名凭据与业务系统调用审批中心的 API Key 是两套独立凭据。

## 4. 系统边界

### 4.1 审批中心负责

- 租户接入和 API Key 认证。
- 人员、租户成员和部门数据。
- 审批流、节点、连线、条件和审批人配置。
- 租户与审批流授权关系。
- 业务动作配置和参数校验。
- 审批申请、实例、任务、意见和操作记录。
- 审批通过后的业务接口调用。
- 执行日志、失败重试、幂等和审计。

### 4.2 业务系统负责

- 业务单据的创建和最终业务状态。
- 选择要使用的 `process_id` 与 `action_code`。
- 组装审批单展示数据和执行参数。
- 校验回调请求并保证业务接口幂等。
- 返回明确的业务执行结果。

### 4.3 上层项目平台负责

- 用户登录和身份认证。
- 将可信用户身份传递给审批中心。
- 后续提供人员、部门等主数据时，与审批中心进行同步或替换手工维护数据。

## 5. 后端模块划分

后端保持一个 FastAPI 应用部署，但代码按照可独立拆分的 server 模块组织。

| 实现顺序 | Server | PostgreSQL Schema | 主要职责 |
|---|---|---|---|
| 1 | tenant | tenant | 可选租户能力、API Key、资源绑定和租户扩展配置 |
| 2 | organization | organization | 全局人员、部门和人员部门关系 |
| 3 | process | process | 审批流、节点、连线、条件及租户授权 |
| 4 | integration | integration | 业务动作、参数规则和回调接口配置 |
| 5 | approval | approval | 申请、实例、运行快照、任务和审批记录 |
| 6 | callback | callback | 执行任务、回调日志、幂等和重试 |

模块先在单体应用中通过接口和数据边界隔离。当调用量、部署节奏或团队分工需要时，再拆成独立服务。

## 6. 数据库约定

### 6.1 Schema

采用“每个 server 一个 PostgreSQL Schema”的规则：

```text
tenant.*
organization.*
process.*
integration.*
approval.*
callback.*
```

业务 Schema 不保存 tenant_id，也不建立指向 tenant Schema 的外键。租户模块通过独立绑定表控制资源归属，例如：

```text
tenant.person_binding
tenant.department_binding
tenant.process_binding
tenant.business_action_binding
tenant.approval_instance_binding
```

业务模块统一调用 TenantScope，不直接查询绑定表。TENANCY_ENABLED=false 时 TenantScope 使用全局空操作实现。

### 6.2 初始化 SQL

所有模块的首次建库结构统一维护在：

```text
backend/data/init.sql
```

新增模块时向该文件追加 Schema、表、外键和索引。初始化 SQL 必须可以重复执行。

正式环境出现结构变更后，需要引入数据库迁移工具；`init.sql` 继续负责全新环境首次建库。

### 6.3 通用字段

核心业务表统一使用：

- UUID 主键。
- 带时区的 UTC 时间。
- 明确的状态字段。
- 创建时间和必要的更新时间。
- 逻辑停用或撤销，避免直接删除审计数据。

## 8. 关键接口链路

### 8.1 租户管理

管理端创建租户后签发 API Key。当前 `/api/admin/*` 使用临时 `X-Admin-Key` 保护，后续替换为项目平台管理员身份。

### 8.2 发起审批

业务系统请求至少包含：

```json
{
  "process_id": "流程ID",
  "action_code": "PAYMENT_EXECUTE",
  "business_key": "PAY-20260920-001",
  "title": "付款申请",
  "applicant_external_id": "U1001",
  "approval_form": {},
  "execution_payload": {}
}
```

服务端处理顺序：

1. 验证 `X-API-Key` 并得到可信租户。
2. 校验租户是否已绑定并启用该 `process_id`。
3. 校验 `action_code` 是否属于当前租户。
4. 校验申请人和参数。
5. 在同一事务中保存申请、实例、运行快照和首批任务。
6. 返回审批实例 ID 和当前状态。

### 8.3 审批操作

审批人只能处理分配给自己的待办任务。审批操作需要记录处理人、动作、意见和时间，并推进后续节点。

第一版至少支持：

- 同意。
- 拒绝。
- 查询待办。
- 查询已办。
- 查询审批详情和完整时间线。

### 8.4 执行业务动作

流程通过后，在审批事务中创建执行任务。后台执行器读取任务后调用业务系统接口，并保存每次尝试。

审批状态和业务执行状态分开表示，例如：

```text
审批状态：APPROVED
执行状态：PENDING / RUNNING / SUCCEEDED / FAILED
```

## 9. 状态建议

### 9.1 租户和配置

- 租户：`ENABLED`、`DISABLED`
- API Key：`ACTIVE`、`REVOKED`
- 流程：`DRAFT`、`ENABLED`、`DISABLED`
- 业务动作：`ENABLED`、`DISABLED`

### 9.2 审批运行

- 申请：`PROCESSING`、`APPROVED`、`REJECTED`、`CANCELLED`
- 任务：`PENDING`、`APPROVED`、`REJECTED`、`CANCELLED`
- 执行：`PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`

## 10. 一致性与可靠性

- 业务系统使用 `business_key` 标识原业务单据。
- 建议对“租户 + business_key + process_id”建立幂等约束。
- 审批推进、任务生成和执行任务创建必须在数据库事务中完成。
- 对外业务动作调用不能放在审批数据库事务中执行。
- 每个执行任务生成稳定幂等键，并传递给业务系统。
- 回调失败按配置重试，人工重试也复用原幂等键。
- 所有审批操作和执行尝试都需要留痕。

## 11. 第一阶段交付标准

第一阶段完成后应能够：

1. 创建和管理租户，签发 API Key。
2. 手工维护人员、租户成员和部门。
3. 在页面配置并启用审批流。
4. 将审批流授权给一个或多个租户。
5. 为租户配置业务动作。
6. 业务系统通过 API Key、`process_id` 和 `action_code` 发起审批。
7. 审批人查看审批单并同意或拒绝。
8. 审批通过后调用业务接口。
9. 查询审批时间线和业务执行结果。
10. 对失败的业务执行进行安全重试。

## 12. 实施顺序

租户模块和人员与组织模块已有第一版实现，但需要先按“可选租户作用域”设计完成解耦重构。后续按以下顺序推进：

1. 租户作用域与人员组织解耦重构。
2. 审批流定义模块。
3. 业务接入与动作配置模块。
4. 审批运行模块。
5. 回调执行模块。
6. 项目平台登录身份适配。
7. 前端管理页面和审批工作台联调。
