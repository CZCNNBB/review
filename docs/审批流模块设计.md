# 审批流模块设计

> 设计状态：已确定第一版范围，待后端实现。

## 1. 模块目标

审批流模块负责在管理页面中创建、编辑和启用审批流程，并把可用流程授权给一个或多个租户。

业务系统发起审批时明确传入 `process_id`。审批中心根据当前流程配置创建审批实例，并立即保存运行快照。之后即使管理员修改流程，也不会改变已经运行中的审批实例。

第一版不提供显式流程版本号。管理员看到和编辑的始终是流程当前配置。

## 2. 核心设计

审批流分为两个层次：

### 2.1 公共流程定义

公共流程描述：

- 流程名称和用途。
- 表单展示与校验规则。
- 节点。
- 节点之间的连线。
- 条件分支。
- 审批方式。

公共流程不直接保存某个租户的具体审批人。

### 2.2 租户流程配置

租户流程配置描述：

- 哪个租户可以使用该流程。
- 当前租户是否启用该流程。
- 公共流程中每个审批节点由当前租户的哪些成员审批。
- 审批人的顺序。

因此同一条“通用付款审批流”可以同时授权给财务系统、采购系统等多个租户，但每个租户配置自己的审批人。

## 3. PostgreSQL Schema

审批流模块使用独立 Schema：

```text
process
```

第一版包含以下表：

```text
process.approval_process
process.approval_form_schema
process.approval_process_node
process.approval_process_edge
```

租户与流程的绑定及租户审批人配置属于可选租户能力，保存在：

```text
tenant.process_binding
tenant.process_node_approver
```

数据库结构统一追加到：

```text
backend/data/init.sql
```

## 4. 流程状态

`approval_process.status` 使用：

| 状态 | 含义 |
|---|---|
| DRAFT | 草稿，不允许业务系统发起 |
| ENABLED | 已启用，可以被配置完成的租户使用 |
| DISABLED | 已停用，不允许创建新实例 |

流程停用只阻止新申请，不影响已经创建的审批实例。

## 5. 节点类型

第一版提供四种节点。

### 5.1 START：开始节点

表示流程入口。

规则：

- 每条流程必须且只能有一个开始节点。
- 不能有入边。
- 至少有一条出边。
- 不执行审批操作。

### 5.2 APPROVAL：审批节点

表示需要人员作出同意或拒绝决定。

配置内容：

- 节点名称。
- 审批方式。
- 前端坐标和展示信息。

具体审批人不保存在公共节点中，而是由每个租户在绑定流程后配置。

### 5.3 CONDITION：条件节点

根据申请数据选择后续分支。

第一版使用结构化条件，不允许管理员直接编写 Python、JavaScript 或 SQL。例如：

```json
{
  "logic": "AND",
  "items": [
    {
      "field": "approval_form.amount",
      "operator": "GT",
      "value": 10000
    },
    {
      "field": "approval_form.currency",
      "operator": "EQ",
      "value": "CNY"
    }
  ]
}
```

支持的第一批操作符：

| 操作符 | 含义 |
|---|---|
| EQ | 等于 |
| NE | 不等于 |
| GT | 大于 |
| GTE | 大于等于 |
| LT | 小于 |
| LTE | 小于等于 |
| IN | 包含在集合中 |
| NOT_IN | 不包含在集合中 |
| IS_EMPTY | 为空 |
| NOT_EMPTY | 不为空 |

条件节点规则：

- 至少有两条出边。
- 每条条件边设置优先级。
- 最多有一条默认分支。
- 按优先级依次判断，第一条命中的边生效。
- 所有条件都未命中时走默认分支。
- 没有默认分支且无条件命中时，实例进入异常状态并等待管理员处理。

### 5.4 END：结束节点

表示流程审批部分结束。

第一版结束结果包括：

- `APPROVED`：审批通过。
- `REJECTED`：审批拒绝。

规则：

- 至少有一条入边。
- 不能有出边。
- 流程中可以有多个结束节点，例如“通过结束”和“拒绝结束”。

当进入 `APPROVED` 结束节点时，审批运行模块创建业务动作执行任务。

审批节点发生拒绝时，第一版默认直接将审批实例结束为 `REJECTED`，不再沿普通出边向后推进。`REJECTED` 结束节点主要用于条件规则主动结束流程。

## 6. 为什么第一版不设置业务动作节点

业务动作属于租户自己的接口配置，而公共审批流可以被多个租户复用。如果把具体付款接口直接写进公共流程节点，会导致流程与某个业务系统耦合。

第一版采用：

```text
业务系统发起审批时传入 action_code
    ↓
流程进入 APPROVED 结束节点
    ↓
审批中心创建 action_code 对应的执行任务
    ↓
回调执行模块调用业务系统
```

因此审批流图只负责“如何审批”，业务接入模块负责“通过后调用什么接口”。

以后如果出现一个流程中需要执行多个自动化动作的明确需求，再增加 `SERVICE_TASK` 节点。

## 7. 审批方式

每个审批节点设置 `approval_mode`。

### 7.1 ANY_ONE：或签

- 节点配置多名审批人。
- 任意一人同意后节点通过。
- 任意一人拒绝后节点拒绝。
- 其他未处理任务自动取消。

### 7.2 ALL：会签

- 节点配置多名审批人。
- 所有人同意后节点通过。
- 任意一人拒绝后节点立即拒绝。
- 拒绝后其他待办任务自动取消。

### 7.3 SEQUENTIAL：顺序审批

- 按租户审批人配置中的 `sort_order` 依次创建或激活任务。
- 当前审批人同意后才轮到下一人。
- 任意一人拒绝后节点立即拒绝。

第一版审批节点必须至少配置一名有效租户成员，不支持动态负责人、部门主管或表达式选人。这些能力后续通过新的 `assignee_type` 扩展。

## 8. 数据表设计

### 8.1 process.approval_process

保存流程基本信息。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 稳定的 process_id |
| code | VARCHAR(64) | 全局唯一流程编码 |
| name | VARCHAR(128) | 流程名称 |
| description | VARCHAR(500) | 可选说明 |
| status | VARCHAR(20) | DRAFT、ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

`id` 一旦创建保持不变，业务系统发起审批时使用该值。

### 8.2 process.approval_form_schema

保存该流程的审批单字段规则和前端展示配置。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| process_id | UUID | 流程 ID，唯一 |
| schema_json | JSONB | 字段类型、必填和数据校验规则 |
| ui_schema_json | JSONB | 标签、顺序、分组和展示组件 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

业务系统发起时提交的 `approval_form` 必须通过 `schema_json` 校验。审批详情按照 `ui_schema_json` 展示。

第一版可以允许空 Schema，表示只把 `approval_form` 当作通用 JSON 展示；正式启用前建议完成字段配置。

### 8.3 process.approval_process_node

保存当前流程节点。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 节点主键 |
| process_id | UUID | 所属流程 |
| node_key | VARCHAR(64) | 流程内稳定且唯一的节点编码 |
| node_type | VARCHAR(20) | START、APPROVAL、CONDITION、END |
| name | VARCHAR(128) | 节点名称 |
| approval_mode | VARCHAR(20) | 审批节点使用 |
| result_status | VARCHAR(20) | END 节点使用 |
| config_json | JSONB | 节点扩展配置 |
| position_json | JSONB | 前端画布坐标 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

新增节点的含义是：在流程图中创建一条新的节点记录，并分配新的 `node_key`。节点是否有效取决于类型配置和连线是否通过完整校验。

### 8.4 process.approval_process_edge

保存节点之间的有向连线。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 连线主键 |
| process_id | UUID | 所属流程 |
| source_node_id | UUID | 起始节点 |
| target_node_id | UUID | 目标节点 |
| name | VARCHAR(100) | 连线名称 |
| priority | INTEGER | 条件判断优先级 |
| condition_json | JSONB | 条件表达式，普通连线为空 |
| is_default | BOOLEAN | 是否为默认分支 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

服务层必须校验起点和终点属于同一流程。

### 8.5 tenant.process_binding

保存租户与审批流的多对多关系。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| tenant_id | UUID | 租户 ID |
| process_id | UUID | 流程 ID |
| status | VARCHAR(20) | ENABLED、DISABLED |
| configuration_status | VARCHAR(20) | READY、INCOMPLETE |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

约束：

- `tenant_id + process_id` 唯一。
- 流程和租户都启用时才允许将关系设置为 `ENABLED`。
- 所有审批节点配置完成后才是 `READY`。
- 业务系统只能使用 `ENABLED + READY` 的关系发起审批。

### 8.6 tenant.process_node_approver

保存某个租户在某个流程审批节点上的具体审批人。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| tenant_process_id | UUID | 租户流程关系 |
| process_node_id | UUID | 公共流程审批节点 |
| person_binding_id | UUID | tenant.person_binding |
| sort_order | INTEGER | 顺序审批时的顺序 |
| created_at | TIMESTAMPTZ | 创建时间 |

约束：

- 审批节点必须属于该 `tenant_process` 对应的流程。
- 租户成员必须属于该 `tenant_process` 对应的租户。
- 只能给 `APPROVAL` 节点配置审批人。
- 同一个成员不能在同一个节点重复配置。
- `SEQUENTIAL` 模式下 `sort_order` 不能重复。

## 9. 流程图保存方式

前端画布每次保存时提交完整流程图：

```json
{
  "nodes": [],
  "edges": []
}
```

后端在一个数据库事务中完成：

1. 校验节点和连线格式。
2. 校验节点引用关系。
3. 新增或更新节点。
4. 删除本次已经移除的节点和连线。
5. 保存新的连线。
6. 执行完整图校验。
7. 更新流程时间。
8. 重新计算所有租户绑定的 `configuration_status`。

整个保存操作成功或失败，不允许只保存一半。

删除公共审批节点时，同时删除该节点尚未进入运行快照的租户审批人配置。已经创建的审批实例不受影响。

## 10. 流程完整性校验

保存流程图和启用流程时都执行校验。

第一版至少包含：

- 恰好一个 START 节点。
- 至少一个 END 节点。
- START 没有入边。
- END 没有出边。
- 每条边的两端节点都存在且属于当前流程。
- 所有节点都能从 START 到达。
- 所有非 END 节点都存在出边。
- 不允许没有出口的死节点。
- APPROVAL 节点配置有效的审批方式。
- CONDITION 节点至少两条出边。
- CONDITION 最多一条默认分支。
- 条件表达式操作符和字段路径合法。
- END 节点具有合法的结果状态。

第一版默认不允许流程图出现环，避免审批实例无限循环。以后确有“退回重审”需求时，通过专门的退回规则实现，不直接开放任意环路。

## 11. 流程修改与运行快照

流程没有显式版本表，但审批实例创建时必须复制：

- 流程基本信息。
- 表单 Schema。
- 全部节点。
- 全部连线和条件。
- 当前租户为每个节点配置的审批人。
- 审批方式和顺序。

快照进入 `approval` Schema，由后续审批运行模块维护。

修改当前流程后的效果：

| 对象 | 是否受影响 |
|---|---|
| 修改前已经创建的审批实例 | 不受影响，继续使用原快照 |
| 修改后新创建的审批实例 | 使用最新配置 |
| 被删除的审批节点对应历史记录 | 保留在实例快照中 |
| 新增审批节点 | 各租户需补充审批人配置 |

当新增审批节点或删除有效审批人后，受影响的租户流程关系自动变为 `INCOMPLETE`，暂时拒绝新申请，直到配置完整。

## 12. 管理接口设计

管理接口第一版继续使用 `X-Admin-Key`。

### 12.1 流程基本信息

```text
POST  /api/admin/processes
GET   /api/admin/processes
GET   /api/admin/processes/{process_id}
PATCH /api/admin/processes/{process_id}
POST  /api/admin/processes/{process_id}/enable
POST  /api/admin/processes/{process_id}/disable
```

### 12.2 流程图和表单

```text
GET  /api/admin/processes/{process_id}/graph
PUT  /api/admin/processes/{process_id}/graph
POST /api/admin/processes/{process_id}/validate
GET  /api/admin/processes/{process_id}/form-schema
PUT  /api/admin/processes/{process_id}/form-schema
```

### 12.3 租户流程关系

```text
PUT   /api/admin/tenants/{tenant_id}/processes/{process_id}
GET   /api/admin/tenants/{tenant_id}/processes
GET   /api/admin/tenants/{tenant_id}/processes/{process_id}
PATCH /api/admin/tenants/{tenant_id}/processes/{process_id}
```

### 12.4 租户审批人配置

```text
GET /api/admin/tenants/{tenant_id}/processes/{process_id}/approvers
PUT /api/admin/tenants/{tenant_id}/processes/{process_id}/nodes/{node_id}/approvers
```

`PUT approvers` 使用全量替换语义，便于前端保存节点当前审批人列表。

## 13. 管理页面效果

审批流管理页面建议分为三层。

### 13.1 流程列表

展示：

- 流程名称和编码。
- 当前状态。
- 节点数量。
- 已绑定租户数量。
- 更新时间。
- 编辑、启停和租户配置入口。

### 13.2 流程设计器

左侧节点面板：

- 开始。
- 审批。
- 条件。
- 结束。

中间画布：

- 拖入节点。
- 拖线连接。
- 调整位置。
- 查看节点错误。

右侧配置面板：

- 节点名称。
- 审批方式。
- 条件表达式。
- 结束结果。
- 表单字段设置。

保存时前端提交完整图，后端返回结构校验结果。

### 13.3 租户配置

选择一个已绑定租户后，为流程中的每个审批节点配置：

- 审批成员。
- 顺序。
- 当前配置是否完整。

页面顶部展示 `READY` 或 `INCOMPLETE`。只有 `READY` 才能启用租户流程。

## 14. 示例

公共付款审批流：

```text
开始
  ↓
部门负责人审批
  ↓
金额是否大于 10000？
  ├─ 否 → 审批通过
  └─ 是 → 财务审批 → 审批通过
```

租户 A 的审批人：

```text
部门负责人审批 → 张三
财务审批       → 李四、王五（会签）
```

租户 B 的审批人：

```text
部门负责人审批 → 赵六
财务审批       → 钱七、孙八（会签）
```

两者使用同一个 `process_id`、流程结构和审批方式，但审批成员来自各自租户。

## 15. 第一版边界

第一版不实现：

- 显式流程版本管理。
- 任意脚本条件。
- 任意环路。
- 动态部门主管。
- 按角色、岗位或表达式自动选人。
- 加签、转交、委托和退回修改。
- 子流程。
- 定时器节点。
- 业务动作节点。
- 流程导入导出。

这些能力通过后续新增节点类型和审批策略扩展，不改变当前流程、租户配置和运行快照三层结构。

## 16. 完成标准

审批流模块完成后应满足：

1. 可以创建、修改、启停流程。
2. 可以通过前端提交完整节点和连线图。
3. 可以校验流程结构并返回明确错误。
4. 可以维护审批表单 Schema。
5. 可以把流程绑定给多个租户。
6. 可以为每个租户分别配置节点审批人。
7. 可以计算租户流程配置是否完整。
8. 只有 `ENABLED + READY` 的租户流程可以被发起。
9. 修改流程不会影响已经创建的审批实例。
10. 数据库结构加入统一 `data/init.sql`。
