# 审批流模块设计

> 设计状态：第一版实施方案已确认，待按模块顺序实现。

## 1. 模块目标

审批流模块负责在管理页面中创建、编辑和启用审批流程，并把可用流程授权给一个或多个租户。

业务系统发起审批时明确传入 `process_id`。审批中心根据当前流程配置创建审批实例，并立即保存运行快照。之后即使管理员修改流程，也不会改变已经运行中的审批实例。

第一版不提供显式流程版本号。管理员看到和编辑的始终是流程当前配置。

## 2. 核心设计

审批流采用“节点能力、流程编排、租户使用范围、运行快照”四层结构。

### 2.1 节点能力层

节点定义只描述一种节点具备什么功能、允许配置哪些字段以及由哪个执行器处理，不保存流程位置、业务名称或具体审批人。

例如 `APPROVAL` 只表示“创建审批任务并等待审批结果”。“第一次审批”“财务复核”“最终审批”都是把这个节点定义拖入流程后产生的不同节点实例。

### 2.2 流程编排层

流程编排描述：

- 流程名称和用途。
- 表单展示与校验规则。
- 流程中的节点实例，也就是每次拖入画布后形成的独立“珠子”。
- 节点实例之间的有向连线，也就是连接“珠子”的“线”。
- 每个节点实例自己的名称、审批方式、具体审批人、条件和画布位置。

同一个节点定义可以在一条流程中使用多次。每次拖入都会创建不同的 `process_node_id` 和 `node_key`，不同实例之间的配置互不影响。

一条审批流保存成功后就是完整、可执行的定义，类似一个已经编排好的 Agent。审批人属于流程节点实例配置，不会因为调用租户不同而变化。

### 2.3 租户使用范围层

- 哪个租户可以使用该流程。
- 当前租户是否启用与该 `process_id` 的关联。

租户关联不保存或覆盖节点、连线、条件、审批方式和审批人。租户 B 直接使用流程 A 时，执行内容与租户 A 完全相同，流程 A 节点中配置的审批人仍然是 A。

如果租户 B 需要相同结构但不同审批人，应复制流程 A 生成新的流程 B，再修改流程 B 的节点实例配置，并把流程 B 授权给租户 B。

### 2.4 运行快照层

审批发起时复制当时使用的流程图、全部节点实例、连线和审批人配置。后台之后把流程节点的审批人从 A 改为 B，只影响新申请，已经运行的实例继续由快照中的 A 处理。

## 3. PostgreSQL Schema

审批流模块使用独立 Schema：

```text
process
```

第一版包含以下表：

```text
process.node_definition
process.approval_process
process.approval_form_schema
process.approval_process_node
process.approval_process_edge
process.process_node_approver
```

租户与流程的使用权绑定属于可选租户能力，保存在：

```text
tenant.process_binding
```

第一版总计 7 张表：`process` Schema 6 张节点和流程编排表，`tenant` Schema 1 张流程使用权绑定表。流程定义表不保存 `tenant_id`。

数据库结构统一追加到：

```text
backend/data/init.sql
```

## 4. 流程状态

`approval_process.status` 使用：

| 状态 | 含义 |
|---|---|
| DRAFT | 草稿，不允许业务系统发起 |
| ENABLED | 已启用且定义完整，可以被已授权租户使用 |
| DISABLED | 已停用，不允许创建新实例 |

流程停用只阻止新申请，不影响已经创建的审批实例。

## 5. 节点能力定义

第一版在 `process.node_definition` 中注册四种节点能力。它们构成前端流程设计器的节点面板，但不会直接成为某条流程中的节点；用户每拖入一次，才会创建一条独立的 `approval_process_node` 实例。

### 5.1 START：开始节点

表示流程入口。

规则：

- 每条流程必须且只能有一个开始节点。
- 不能有入边。
- 至少有一条出边。
- 不执行审批操作。

### 5.2 APPROVAL：审批节点

表示需要人员作出同意或拒绝决定。

配置内容：

- 节点名称。
- 审批方式。
- 前端坐标和展示信息。

具体审批人不保存在节点定义中，而是作为流程节点实例的子配置保存在 `process.process_node_approver`。审批流保存后，审批人就是该流程定义的一部分。

### 5.3 CONDITION：条件节点

根据申请数据选择后续分支。

第一版使用结构化条件，不允许管理员直接编写 Python、JavaScript 或 SQL。例如：

```json
{
  "logic": "AND",
  "items": [
    {
      "field": "approval_form.amount",
      "operator": "GT",
      "value": 10000
    },
    {
      "field": "approval_form.currency",
      "operator": "EQ",
      "value": "CNY"
    }
  ]
}
```

支持的第一批操作符：

| 操作符 | 含义 |
|---|---|
| EQ | 等于 |
| NE | 不等于 |
| GT | 大于 |
| GTE | 大于等于 |
| LT | 小于 |
| LTE | 小于等于 |
| IN | 包含在集合中 |
| NOT_IN | 不包含在集合中 |
| IS_EMPTY | 为空 |
| NOT_EMPTY | 不为空 |

条件节点规则：

- 至少有两条出边。
- 每条条件边设置优先级。
- 最多有一条默认分支。
- 按优先级依次判断，第一条命中的边生效。
- 所有条件都未命中时走默认分支。
- 没有默认分支且无条件命中时，实例进入异常状态并等待管理员处理。

### 5.4 END：结束节点

表示流程审批部分结束。

第一版结束结果包括：

- `APPROVED`：审批通过。
- `REJECTED`：审批拒绝。

规则：

- 至少有一条入边。
- 不能有出边。
- 流程中可以有多个结束节点，例如“通过结束”和“拒绝结束”。

当进入 `APPROVED` 结束节点时，审批运行模块创建业务动作执行任务。

审批节点发生拒绝时，第一版默认直接将审批实例结束为 `REJECTED`，不再沿普通出边向后推进。`REJECTED` 结束节点主要用于条件规则主动结束流程。

## 6. 为什么第一版不设置业务动作节点

业务动作属于租户自己的接口配置，而公共审批流可以被多个租户复用。如果把具体付款接口直接写进公共流程节点，会导致流程与某个业务系统耦合。

第一版采用：

```text
业务系统发起审批时传入 action_code
    ↓
流程进入 APPROVED 结束节点
    ↓
审批中心创建 action_code 对应的执行任务
    ↓
回调执行模块调用业务系统
```

因此审批流图只负责“如何审批”，业务接入模块负责“通过后调用什么接口”。

以后如果出现一个流程中需要执行多个自动化动作的明确需求，再增加 `SERVICE_TASK` 节点。

## 7. 审批方式

每个审批节点设置 `approval_mode`。

### 7.1 ANY_ONE：或签

- 节点配置多名审批人。
- 任意一人同意后节点通过。
- 任意一人拒绝后节点拒绝。
- 其他未处理任务自动取消。

### 7.2 ALL：会签

- 节点配置多名审批人。
- 所有人同意后节点通过。
- 任意一人拒绝后节点立即拒绝。
- 拒绝后其他待办任务自动取消。

### 7.3 SEQUENTIAL：顺序审批

- 按节点审批人配置中的 `sort_order` 依次创建或激活任务。
- 当前审批人同意后才轮到下一人。
- 任意一人拒绝后节点立即拒绝。

第一版审批节点必须至少配置一名已启用的全局人员，不支持动态负责人、部门主管或表达式选人。这些能力后续通过新的 `assignee_type` 扩展。

## 8. 数据表设计

### 8.1 process.node_definition

保存节点功能定义和前端配置契约，不保存任何流程实例内容或审批人员。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 节点定义主键 |
| type_code | VARCHAR(64) | 全局唯一能力编码，例如 APPROVAL |
| name | VARCHAR(100) | 节点面板展示名称 |
| description | VARCHAR(500) | 能力说明 |
| icon | VARCHAR(100) | 前端图标标识 |
| handler_key | VARCHAR(100) | 后端执行器标识 |
| config_schema_json | JSONB | 节点实例允许配置的字段规则 |
| ui_schema_json | JSONB | 节点配置面板展示规则 |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

节点定义控制“能做什么”。新增一条审批流或在流程中重复使用已有节点能力都不需要修改代码；只有新增一种后端从未支持过的执行行为时，才需要实现新的 `handler_key` 执行器。

### 8.2 process.approval_process

保存流程基本信息。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 稳定的 process_id |
| code | VARCHAR(64) | 全局唯一流程编码 |
| name | VARCHAR(128) | 流程名称 |
| description | VARCHAR(500) | 可选说明 |
| status | VARCHAR(20) | DRAFT、ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

`id` 一旦创建保持不变，业务系统发起审批时使用该值。

第一版不提供物理删除流程接口。无效流程使用 `DISABLED`，避免业务系统保存的 `process_id` 失去对应记录。

### 8.3 process.approval_form_schema

保存该流程的审批单字段规则和前端展示配置。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| process_id | UUID | 流程 ID，唯一 |
| schema_json | JSONB | 字段类型、必填和数据校验规则 |
| ui_schema_json | JSONB | 标签、顺序、分组和展示组件 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

业务系统发起时提交的 `approval_form` 必须通过 `schema_json` 校验。审批详情按照 `ui_schema_json` 展示。

第一版可以允许空 Schema，表示只把 `approval_form` 当作通用 JSON 展示；正式启用前建议完成字段配置。

### 8.4 process.approval_process_node

保存当前流程节点。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 流程节点实例主键 |
| process_id | UUID | 所属流程 |
| node_definition_id | UUID | 使用的节点能力定义 |
| node_key | VARCHAR(64) | 流程内稳定且唯一的节点编码 |
| name | VARCHAR(128) | 当前节点实例名称 |
| approval_mode | VARCHAR(20) | 审批节点使用 |
| result_status | VARCHAR(20) | END 节点使用 |
| config_json | JSONB | 节点扩展配置 |
| position_json | JSONB | 前端画布坐标 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

新增节点的含义是：选择一条节点定义，在流程图中创建一条新的节点实例记录，并分配新的 `id` 和 `node_key`。即使多次选择同一个节点定义，每次生成的实例也相互独立。

`node_key` 由前端创建节点时生成并在后续编辑中保持不变。完整流程图请求中的连线使用 `source_node_key` 和 `target_node_key` 引用节点，后端保存时解析为 `source_node_id` 和 `target_node_id`，避免新节点尚无数据库 ID 时无法连线。

### 8.5 process.approval_process_edge

保存节点之间的有向连线。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 连线主键 |
| process_id | UUID | 所属流程 |
| source_node_id | UUID | 起始节点 |
| target_node_id | UUID | 目标节点 |
| name | VARCHAR(100) | 连线名称 |
| priority | INTEGER | 条件判断优先级 |
| condition_json | JSONB | 条件表达式，普通连线为空 |
| is_default | BOOLEAN | 是否为默认分支 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

服务层必须校验起点和终点属于同一流程。

### 8.6 process.process_node_approver

保存流程中某个具体审批节点实例配置的审批人。审批人属于流程编排本身，与使用该流程的租户无关。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| process_node_id | UUID | 流程中的具体审批节点实例 ID |
| person_id | UUID | organization.person ID |
| sort_order | INTEGER | 顺序审批时的顺序 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

约束：

- `process_node_id + person_id` 唯一。
- 只能给 `APPROVAL` 类型的节点实例配置审批人。
- 人员必须存在且状态为 `ENABLED`。
- `SEQUENTIAL` 模式下，同一节点的 `sort_order` 不能重复。
- `process_node_id` 可以关联 `process.approval_process_node`。
- `person_id` 不建立指向 `organization` Schema 的跨 Schema 外键，由流程服务在保存前校验。

同一个节点定义在一条流程中出现多次时，每次都会产生不同的 `process_node_id`，因此可以分别配置不同审批人。

### 8.7 tenant.process_binding

只保存租户与审批流的使用权关系，不保存或覆盖流程中的节点、连线、条件和审批人。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| tenant_id | UUID | 租户 ID |
| process_id | UUID | 可以使用的流程 ID |
| status | VARCHAR(20) | ENABLED、DISABLED |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

约束：

- `tenant_id + process_id` 唯一。
- 业务系统只能使用状态为 `ENABLED` 的绑定。
- 发起审批时，流程本身也必须处于 `ENABLED` 状态并通过完整性校验。
- `process_id` 不建立指向 `process` Schema 的数据库外键，由绑定服务在写入前校验流程存在。

租户 B 直接绑定流程 A 后，执行的仍然是流程 A 中已经保存好的审批人。如果租户 B 需要修改审批人，应复制流程 A 得到流程 B，修改流程 B 后再建立绑定。

## 9. 流程图保存方式

前端画布每次点击保存时提交完整流程图，其中审批人是节点实例配置的一部分：

```json
{
  "nodes": [
    {
      "node_key": "finance_approval",
      "node_definition_code": "APPROVAL",
      "name": "财务审批",
      "approval_mode": "ALL",
      "approvers": [
        {
          "person_id": "人员UUID",
          "sort_order": 1
        }
      ],
      "position": {"x": 460, "y": 180}
    }
  ],
  "edges": [
    {
      "source_node_key": "start",
      "target_node_key": "finance_approval"
    }
  ]
}
```

后端在一个数据库事务中完成：

1. 校验节点定义、节点实例和连线格式。
2. 校验人员存在且状态可用。
3. 新增或更新节点实例。
4. 全量替换每个审批节点实例的审批人配置。
5. 删除本次已经移除的节点、审批人配置和连线。
6. 保存新的连线。
7. 执行完整流程图校验。
8. 更新流程时间。

整个保存操作成功或失败，不允许只保存一半。

删除流程中的节点实例时，同时删除该实例的审批人配置。节点定义本身和其他使用相同定义的节点实例不受影响，已经创建的审批实例也不受影响。

## 10. 流程完整性校验

保存流程图和启用流程时都执行校验。第一版至少包含：

- 每个节点实例引用的节点定义存在且状态可用。
- 节点实例配置符合节点定义的 `config_schema_json`。
- 恰好一个 START 节点。
- 至少一个 END 节点。
- START 没有入边。
- END 没有出边。
- 每条边的两端节点都存在且属于当前流程。
- 所有节点都能从 START 到达。
- 所有非 END 节点都存在出边。
- 不允许没有出口的死节点。
- APPROVAL 节点配置合法的审批方式和至少一名有效审批人。
- CONDITION 节点至少有两条出边，且最多一条默认分支。
- 条件表达式的操作符和字段路径合法。
- END 节点具有合法的结果状态。

第一版默认不允许流程图出现环，避免审批实例无限循环。以后确有退回重审需求时，通过专门的退回规则实现。

只有完整性校验通过的流程才能设置为 `ENABLED`。租户绑定不再保存 `READY/INCOMPLETE`，因为流程是否完整是流程自身的属性，不随租户变化。

## 11. 流程复制、修改与运行快照

### 11.1 复制流程

复制流程时创建新的 `process_id`，并复制：

- 流程基本信息，流程编码需要重新指定。
- 表单 Schema。
- 全部节点实例，并生成新的节点实例 ID。
- 每个节点实例的审批人配置。
- 全部连线，并重新指向复制后的节点实例。

复制完成后，新流程默认保存为 `DRAFT`。管理员可以修改其中任意节点的审批人，再启用并授权给其他租户。

### 11.2 修改流程

流程没有显式版本表。修改流程只改变当前定义：

- 修改前已经创建的审批实例不受影响。
- 修改后新创建的审批实例使用最新配置。
- 删除节点不会删除历史实例中的节点记录。
- 把节点审批人从 A 改为 B，只影响修改后新发起的申请。

### 11.3 运行快照

业务系统发起审批时，审批运行模块必须复制当时实际使用的：

- 流程基本信息。
- 表单 Schema。
- 全部节点实例。
- 全部连线和条件。
- 每个审批节点实例的审批人。
- 审批方式和顺序。

快照进入 `approval` Schema。审批实例创建后只读取自己的运行快照，不再读取可能继续变化的流程定义。

例如上午发起时流程为 `A → B`，中午管理员把流程改为 `A → C`：上午的实例仍按 `A → B` 运行，中午修改后新发起的实例才按 `A → C` 运行。

## 12. 管理接口设计

管理接口第一版继续使用 `X-Admin-Key`。

### 12.1 节点定义

```text
POST  /api/admin/node-definitions
GET   /api/admin/node-definitions
GET   /api/admin/node-definitions/{node_definition_id}
PATCH /api/admin/node-definitions/{node_definition_id}
```

新增节点定义时，`handler_key` 必须是后端已经注册的执行器。页面可以管理节点名称、图标和配置 Schema，但不能仅靠任意字符串创造后端不存在的执行行为。

### 12.2 流程基本信息和复制


## 13. 管理页面效果

### 13.1 流程列表

展示流程名称、编码、状态、节点数量、已绑定租户数量和更新时间，并提供编辑、复制、启停和租户授权入口。

### 13.2 流程设计器

左侧节点面板从 `process.node_definition` 动态加载可用节点能力。同一个节点定义可以重复拖入画布，每次拖入都生成独立节点实例。

中间画布负责节点摆放、连线和错误展示。右侧配置面板负责当前节点实例的名称、审批方式、具体审批人、条件、结束结果和其他配置。

点击保存时，前端提交完整节点、节点审批人和连线，后端以单个事务保存。

### 13.3 租户授权

租户页面只选择允许使用的审批流并设置绑定状态，不配置审批人。流程内容在绑定前已经保存完整。

## 14. 示例

流程 A：

```text
开始
  ↓
第一次审批（通用 APPROVAL 节点实例 N01，审批人 A）
  ↓
最终审批（通用 APPROVAL 节点实例 N02，审批人 A）
  ↓
结束
```

租户 A 绑定流程 A 后，按照流程 A 的配置由 A 审批。

租户 B 如果直接绑定流程 A，仍然按照流程 A 的配置由 A 审批。租户 B 想把最终审批人改成 B 时，执行：

```text
复制流程 A
    ↓
得到流程 B（新 process_id）
    ↓
把流程 B 的 N02 对应节点实例审批人改成 B
    ↓
启用流程 B
    ↓
把流程 B 授权给租户 B
```

流程 A 与流程 B 后续可以独立修改，互不影响。

## 15. 第一版边界

第一版不实现：

- 显式流程版本管理。
- 租户维度的节点配置覆盖。
- 任意脚本条件。
- 任意环路。
- 动态部门主管。
- 按角色、岗位或表达式自动选人。
- 加签、转交、委托和退回修改。
- 子流程。
- 定时器节点。
- 业务动作节点。
- 流程导入导出。

这些能力通过后续新增节点能力和审批策略扩展，不改变当前节点能力、流程编排、租户使用范围和运行快照四层结构。

## 16. 完成标准

审批流模块完成后应满足：

1. 可以创建、修改、复制、启停流程。
2. 可以通过前端提交完整节点、节点审批人和连线图。
3. 同一个节点定义可以在同一流程中重复使用并配置不同审批人。
4. 可以校验流程结构并返回明确错误。
5. 可以维护审批表单 Schema。
6. 可以把流程授权给多个租户，且所有租户执行相同流程内容。
7. 租户不覆盖流程中的审批人。
8. 只有绑定状态和流程状态均为 `ENABLED` 时才允许发起。
9. 修改流程不会影响已经创建的审批实例。
10. 数据库结构加入统一 `data/init.sql`。

## 17. 分步实现顺序

1. 创建 `process` 模块和 `node_definition`，注册第一批节点执行器。
2. 实现流程、表单、节点实例、连线和节点审批人 5 张编排表。
3. 实现完整流程图保存、读取和结构校验。
4. 实现流程复制，并正确复制节点、审批人和连线引用。
5. 在 `tenant` 模块增加只控制使用权的 `process_binding`。
6. 实现流程启停、租户授权和发起前校验。
7. 补齐管理 API、测试和统一初始化 SQL。

本阶段只完成“可配置、可校验、可复制、可授权”的审批流定义，不在本模块中创建审批实例或执行回调；这两部分分别由后续 `approval` 和 `callback` 模块负责。
